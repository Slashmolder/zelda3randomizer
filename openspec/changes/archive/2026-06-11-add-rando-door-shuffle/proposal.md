## Why

Door shuffle is the most ambitious randomizer axis on the roadmap: it randomizes the **internal door-to-door connections inside dungeons**, not just which overworld door reaches which dungeon (that is the already-shipped entrance shuffle). After a door shuffle, Eastern Palace's lobby might open onto Swamp's flooded hub; a small-key door that vanilla puts three rooms deep might gate the first room. It is the headline feature of the upstream **ALttPDoorRandomizer** project, the reference for this change.

This change exists because door shuffle is *architecturally novel for this fork*, and the plan must be gotten right before code lands. Four research findings frame everything:

1. **The runtime engine has NO normal-door destination table.** Unlike the SNES ROM (which ALttPDoorRandomizer patches), the zelda3 C reimplementation computes a normal edge-door's destination *positionally* — walking off the east edge of room `R` loads `R+1`, north loads `R-0x10` (`Dungeon_StartInterRoomTrans_Right/Left/Up/Down`, `src/dungeon.c:8188, 2059, 2099, 2142`). There is nothing to "patch." Redirecting a door means **adding an indirection layer** at those four functions (plus the staircase/hole/teleport-door sites). The good news: the engine *already* has the exact primitive needed — the vanilla **teleport-door** path reads an arbitrary destination room from the room header and calls `Dungeon_AdjustForTeleportDoors` (`src/dungeon.c:8149`) to reposition Link + camera into any room. Door shuffle generalizes that one mechanism to every shuffled door.

2. **The staircase/hole/teleport subset IS already table-driven.** Those transitions read `dung_hdr_travel_destinations[0..4]` (room-header bytes 9–13). They can be redirected by overriding five bytes per room — far easier than the positional normal-door case.

3. **The logic engine cannot express intra-dungeon connectivity today.** Reachability is a *region graph where an entire dungeon is one node* and small keys are modeled as inventory *count thresholds* baked for the vanilla layout (`HAS_AMOUNT(SmallKey_PalaceOfDarkness, 5)` etc. in `assets/rando/logic_parts/*.yaml`). A shuffled door layout changes which locations sit behind how many keys and whether they are reachable at all — none of which is expressible in the shipped graph. Door shuffle needs a **new per-seed dungeon-interior solver** feeding the placer.

4. **The reference is ~550 KB of Python** (`DoorShuffle.py` 247 KB + `DungeonGenerator.py` 198 KB + `KeyDoorShuffle.py` 108 KB). The hardest parts — the cross-dungeon polarity/sector-distribution engine and the exponential key-door softlock prover — must be reimplemented in C. We do **not** need seed-parity with ALttPDoorRandomizer (we define our own door-layout format + RNG salt), which frees the port from replicating Python dict-iteration order.

Because the runtime risk and the generation risk are independent and both large, this change is **staged so each milestone is independently shippable and playtestable**, and the committed scope is the de-risking foundation plus a playable basic MVP. The full design (all intensities, crossed dungeons, door-type/trap/decouple shuffle) is captured in `design.md` and split into explicit follow-on changes.

## What Changes (committed scope = Milestones A + B)

**Milestone A — Foundations & identity (de-risk the runtime layer with zero behavior change):**
- Codegen the **static door/room topology** from the reference (`assets/scripts/gen_door_tables.py`, which builds the reference's vanilla world in-process and harvests it) into **committed** C tables (`src/rando/door_tables.gen.{c,h}` + `assets/rando/door_predicates.gen.json` — committed because CI lacks the reference checkout; `check_door_tables.py` guards consistency): a canonical door-stub catalog (frozen ids in `door_registry.yaml`), each stub's type/kind/default partner/door-list position, regions, edges + rule blobs, locations, events, drop keys, and portals.
- A runtime **sparse door-redirect layer** (`src/rando/door_runtime.{c,h}` new): a per-seed link table with a `NO_OVERRIDE` sentinel, consulted at the **intensity-1 sites only** — the four `Dungeon_StartInterRoomTrans_*` supertile-boundary branches and the spiral header-dest read in `Dungeon_DetectStaircase` (hole/teleport/straight-stair sites untouched, follow-on) — behind a new `kFeatures1_DoorShuffleActive` bit. **Identity = flag ON + every link `NO_OVERRIDE` ⇒ byte-for-byte vanilla behavior** (RAM-compare clean, corpus untouched).
- The generalized **arbitrary-room arrival** routine (`DoorRt_Arrive`, generalizing `Dungeon_AdjustForTeleportDoors` to an arrival edge/slot/layer) + camera/quadrant/layer coherence, and a spiral intra-room fixup applied after the destination room loads.

**Milestone B — Basic door shuffle MVP (playable, beatable, softlock-free):**
- A new **door-shuffle generator** behind the `shuffle_doors.h` contract (`DoorShuffle_Generate` / `DoorShuffle_LayoutDigest` / `DoorExplore_Run`): `door_shuffle = basic` (within a single dungeon), `intensity = 1` (normal + spiral-stair doors only), `door_type_mode = original` (vanilla small-key-door counts, positions re-chosen + prover-validated; big-key doors stay put), in-dungeon small + big keys forced. Ported from the reference's **live** pipeline: the crystal-aware explorer, the stitcher (`source/dungeon/DungeonStitcher.py generate_dungeon`'s random-proposal + local-repair), and the **key-door softlock prover** (`analyze_dungeon`/`validate_key_layout` ⇒ worst-case per-door thresholds + `bk_restricted`). Single-dungeon only ⇒ **skipping the hardest component (the polarity engine).** A runtime **door-KIND overlay** makes relocated key doors physically real (three door-list reader seams; pos<4 stateful-position swap; partner open-bit mirror). MVP pins: Open/Standard + NoGlitches only; mutually exclusive with entrance shuffle; Hyrule Castle (all world states) + Swamp Palace pinned.
- **Logic half (as built — Arch-2)**: two new STATIC predicate-VM ops `OP_DOORS_ACTIVE(dungeon)` / `OP_DOORS_LOC_REACHABLE(loc)`; codegen wraps every door-controlled location's `can_reach` as `(NOT ACTIVE AND vanilla) OR (ACTIVE AND LOC_REACHABLE)`; the ops query a **reachability oracle that runs the SAME explorer the stitcher/prover use**, seeded from a committed per-portal gate table (`door_portals.yaml`), with worst-case key thresholds (conservative-safe) and the drop-key economy, memoized per fixed-point pass. `bk_restricted` is a real big-key placement ban in the placer. NOTE: the pre-review plan to inject *arbitrary* per-seed predicates through the existing override seam was found **infeasible** (that seam carries static-stream offsets only), and the interim per-room-region static port was superseded by the oracle — see `design.md §4`. Inactive ⇒ the vanilla predicate bytes evaluate ⇒ vanilla reachability byte-identical.
- **Settings / save / generation / UI** plumbing: `door_shuffle` in canonical pad byte `[27]` bits 0-1; sidecar `door_attempt` @76 + 24-bit layout digest @77-79 with a **blocking activation hard-fail on drift**; the door phase in BOTH generation pipelines (slot + headless); spoiler section + settings-window checkbox. `kGeneratorVersion`/corpus close-out lands with the in-flight stitcher.

## Capabilities

### New Capabilities

- **`randomizer-door-runtime`** — the in-game door-transition redirection engine: the per-seed door-link table, the four transition-site hooks, the generalized arbitrary-room arrival (Link position + camera + quadrant + plane/floor), and the environment/shutter coherence rules. Peer to `randomizer-inverted-runtime`.

### Modified Capabilities

- **`randomizer-shuffles`** — ADDED Requirement "Door shuffle generation": the `door_shuffle` axis (committed scope: `basic` + intensity 1 + `original` door types), the MVP pins (Open/Standard + NoGlitches, entrance-shuffle mutual exclusion, in-dungeon keys, HC + Swamp pinned), the live-stitcher port, and the key-door softlock prover, with a beatability + no-softlock + determinism contract.
- **`randomizer-logic`** — ADDED Requirements "Door-shuffle reachability via static oracle ops (Arch-2)", "Oracle portal seeding from a committed gate table", and "Drop-key economy shared by prover and oracle": the `OP_DOORS_*` ops + codegen wrap (inert when off ⇒ `door_shuffle == vanilla` byte-identical reachability, corpus invariant preserved), oracle = the generator's explorer.
- **`randomizer-placement`** — ADDED Requirement: assumed-fill sees the layout through the wrapped oracle predicates; `bk_restricted` enforced as a big-key placement ban; the `door_attempt` retry loop; in-dungeon containment stays consistent with the door layout.
- **`randomizer-core`** — ADDED Requirement: the `door_shuffle` axis in canonical serialization (committed scope packs into pad byte `[27]` bits 0-1; the full feature's wider axes are flagged as requiring the `kSettingsCanonicalLen` cascade). Authored as ADDED, not MODIFIED, because the baseline "Settings canonical serialization order" requirement is stale relative to the as-built `[25]/[26]` axes — see `design.md §5`.
- **`randomizer-save`** — ADDED Requirement: the door layout is **regenerated from `(seed, settings, door_attempt)` at load, not serialized**; `door_attempt` @76 + a 24-bit layout digest @77-79 claim the reserved sidecar tail. Drift is **blocking**: activation regenerates, recomputes the digest, and hard-fails (refuses the slot, non-destructively) on mismatch — unlike entrance shuffle's non-blocking warning.

## Impact

- **Code (new):** `src/rando/door_runtime.{c,h}`, `src/rando/shuffle_doors.{c,h}`, `src/rando/door_keylogic.{c,h}` (the key-door prover), `assets/scripts/gen_door_tables.py`, `assets/rando/door_registry.yaml` (stable door-stub ids). **Code (touched):** `src/dungeon.c` (≈6 transition-site hooks + generalized arrival), `src/rando/rando_settings.{c,h}`, `src/rando/rando_save.{c,h}`, `src/rando/rando_generate.c`, `src/rando/rando.c` (slot-load regen + runtime install/teardown), `src/rando/rando_logic.c` (per-seed door-graph + per-room regions + reachability-cap bump), `src/rando/rando_placement.c`, `src/features.h` (new flag + runtime RAM), `src/rando/rando_window/*` (UI), `assets/scripts/{bump,run}_rando_corpus.py`.
- **Assets:** the codegen output is **committed** (`src/rando/door_tables.gen.{c,h}`, `assets/rando/door_predicates.gen.json` — CI lacks the reference checkout to regenerate; see `design.md §9.7`); `check_door_tables.py` + a self-test still guard the fails-open class (missing/empty/inconsistent tables, see `design.md §10`).
- **Effort / bottleneck:** Large — comparable to the original randomizer-support change. The real bottleneck is **not** token volume but the **playtest loop**: the slot path has no automated net (corpus + `--rando-selftest` cover only generation, never the runtime door redirect or the key prover's end-to-end correctness), so every milestone is gated on hand-playtesting redirected dungeons. Milestone A's identity test is the one piece with an automatable check (corpus byte-identical).
- **Regression risk:** `kGeneratorVersion` bumps; corpus regenerates. `doorShuffle == vanilla` MUST stay byte-identical (Milestone A enforces it before any shuffle exists).
- **Out of scope (follow-on changes, designed but not built here):** intensity 2/3 (open-edges, straight-stairs, ladders, lobby/portal shuffle — couples with entrance shuffle); `door_type_mode` big/all/chaos + trap-door shuffle/removal; decouple (one-way) doors; **crossed/partitioned** modes (the polarity/sector-distribution engine + cross-dungeon environment porting — the single hardest runtime+gen surface); wild/universal key modes × door shuffle; pottery/key-drop pools.
- **ALTTPR provenance:** door rando is a **separate codebase** from the ALTTPR PHP this fork otherwise mirrors — none of the placement/logic PHP applies. The reference is an `ALttPDoorRandomizer` checkout (MIT, verify `LICENSE`). Claim-grounding discipline applies: read the actual Python, not memory.

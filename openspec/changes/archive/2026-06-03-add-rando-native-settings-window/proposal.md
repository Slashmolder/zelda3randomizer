## Why

The randomizer settings flow today lives inside the SNES screen: a custom in-game settings screen, an on-screen alphabet picker, and a from-scratch text-input layer (`src/rando/rando_textfield.{c,h}`, plus the settings-screen branch of `src/rando/rando.c` and `src/select_file.c`). That UI was the right Phase A choice when the game was the only window the player had, but it's a poor fit for the actual settings surface: ~20 enum/integer/bool fields with cross-field validation (Triforce Hunt's `pieces_required ≤ pieces_placed`, accessibility = `locations` forced by Completionist, crystal-count interactions), plus the share-string text entry. Doing all of that with a D-pad + on-screen alphabet inside a 256×224 framebuffer is slow, easy to misclick, and a maintenance tax — every new setting (Phase B will add ~10 more) needs new tile rendering, new cursor navigation, and new translation handling. PC players already sit in front of a desktop OS with a mouse, keyboard, and pixel-precise widgets; we should use them.

Replacing the in-game settings UI with a native OS window also unblocks features that don't fit a 256×224 screen at all: a live spoiler/placement browser, search-as-you-type location lookups, copy/paste share strings, multi-column display of all dungeon-item modes at once, and a real preset gallery.

## What Changes

- Add a second OS-native window (Dear ImGui, vendored under `third_party/imgui/`) that runs alongside the existing game window on Windows/Linux/macOS. The window is **created at startup but HIDDEN**; it is shown/raised when the player chooses "New Randomizer" on the file-select kind-toggle, and is re-openable via a hotkey / game menu. Vanilla players never see a second window. Closing it hides (does not destroy) it; closing the game window shuts the app down.
- Render the randomizer settings surface **at parity with the in-game settings screen** — the live-editable axis set the in-game `kRow_*` rows expose (world_state, goal, crystals_ganon, crystals_tower, item_pool_difficulty, the four dungeon_*_mode fields, pieces_required/pieces_placed, mode_weapons, accessibility, prize_shuffle, medallion_shuffle, race_mode, hints), plus presets per `Settings_ApplyPreset`, share-string entry, and asset-hash warning acknowledgement — in the native window using ImGui widgets. Boss/drop/entrance/enemy/glitches shuffle appear only as disabled "coming soon" placeholders (matching the in-game `kRow_*_Disabled` rows), because boss/drop shuffle is runtime-inert for playable slots.
- Add a shared state bridge (`src/rando/rando_window_bridge.{c,h}`) that owns the canonical pending-settings `RandoSettings` struct, exposes thread-safe read/apply primitives, and signals the game side when "Generate & start new slot" is requested.
- On PC builds, the in-game randomizer settings screen, on-screen alphabet picker, and `rando_textfield` text-input layer are **compile-guarded out (not deleted)** behind a new compile-time flag `Z3R_NATIVE_SETTINGS_WINDOW`: defined ⇒ the native window is the live path on PC; undefined ⇒ the in-game screen compiles back in. No in-game code is removed — it stays compilable for Switch and remains flippable on Windows for testing. We ship Windows with the flag defined.
- Keep the in-game settings UI fully intact on Nintendo Switch (Switch has no second-window concept; its text-input gap is already covered by `add-rando-switch-swkbd`). File-select's randomizer-slot rendering, slot banner with the 5-icon hash, and the kind-toggle entry remain in-game on all platforms — only the *settings entry* path moves to the native window on PC. The recommended-features opt-in panel moves **into** the native window on PC (it is only reachable through the in-game settings screen today, which is guarded out on PC); on Switch it stays in-game.
- Persist the user's last-used settings to a **sidecar `saves/rando_window.ini`** holding a `[rando_window]` section so the window opens preselected to their previous configuration. The persisted blob is the same canonical-serialized bytes (`kSettingsCanonicalLen` = 28) that feed `settings_hash` — no parallel format. Persisted as **hex** (56 chars for 28 bytes; no base64 helper exists in the codebase today; see design §D9). The sidecar also carries the `[RandoAssetDecisions]` section so asset-hash "Always allow" decisions persist there; they continue to use the existing `[RandoAssetDecisions]` lookup (`src/config.c`, the asset-decision helpers in `src/select_file.c`) so there is one source of truth. The sidecar is loaded at startup via a new whitelisting `Config_LoadAuxIniFile` that parses only `[rando_window]` + `[RandoAssetDecisions]` and **never rewrites the user's hand-edited `zelda3.ini`**; the in-place `Config_WriteIniFile` rewriter is deferred — see design.md §D9.
- Add a settings-window-only "Generate now" button that runs the existing seed-generation pipeline on the game thread (not the UI thread) and reports progress/errors back into the ImGui window via the bridge.
- Add a read-only Spoiler/Placement viewer tab in the ImGui window (collapsible, hidden by default for race-mode slots) backed by the existing `rando_spoiler` writer output, so the design replaces UI surface area on the SNES side rather than just relocating it.
- Update `main.c`'s SDL init to create two windows (game + settings), pump events for both in the existing main loop, and route ImGui input to the settings window only. The game window's input handling and frame timing are unchanged.

## Capabilities

### New Capabilities

- `randomizer-native-window`: The Dear ImGui-based second OS window that owns the randomizer settings UI on PC builds. Covers hidden-until-needed window lifetime, two-window SDL event pumping, ImGui rendering integration with the existing SDL2+OpenGL stack, the settings-state bridge between window and game, persistence of last-used settings to a sidecar `saves/rando_window.ini`, the Generate-and-apply flow, the recommended-features opt-in (moved into the window on PC), the read-only spoiler/placement viewer, and the Switch-fallback compile guard.

### Modified Capabilities

- `randomizer-ui`: The Text-input infrastructure, On-screen alphabet picker, and Settings screen requirements become **PC-conditional** — they remain in force on Switch builds and are **compile-guarded out (not deleted)** on Windows/Linux/macOS builds when `Z3R_NATIVE_SETTINGS_WINDOW` is defined, where the native window handles those responsibilities; the in-game code stays compilable (flip the guard off to rebuild it). The Three-slot file-select with kind-toggle, 5-icon visual hash, and Slot banner with truncation requirements are unchanged on all platforms. The Recommended-features opt-in panel stays in-game on Switch but moves into the native window on PC (its only in-game entry path is the guarded-out settings screen).

## Impact

- **New code surface**: `third_party/imgui/` (vendored ImGui + SDL2/OpenGL backends, ~10 .cpp/.h files), `src/rando/rando_window/` (new directory: window lifecycle, ImGui rendering of each settings panel, bridge), `src/rando/rando_generate.{c,h}` (shared `Rando_GenerateSlot` extracted from the in-game flow), `src/rando/rando_asset_decisions.{c,h}` (promoted asset-decision helpers), additions to `src/main.c` for the second window, additions to `config.c` for the `[rando_window]` sidecar load/parse.
- **Modified code**: `src/main.c` (SDL init for two windows, event-pump dispatch), `src/select_file.c` (kind-toggle "New Randomizer" branch on PC opens the native window instead of the in-game settings screen; `SelectFile_Settings_HandleGenerate` refactored to call the shared `Rando_GenerateSlot`), `src/rando/rando.c` (settings-screen module entry points compile out under `Z3R_NATIVE_SETTINGS_WINDOW`).
- **Compile-guarded code (PC builds only; NOT deleted)**: the in-game randomizer settings screen module and its tile rendering, the on-screen alphabet picker, and `src/rando/rando_textfield.{c,h}` are wrapped in `#ifndef Z3R_NATIVE_SETTINGS_WINDOW` (and excluded from the PC build list) when the guard is defined; flipping the guard off recompiles them. Switch builds (guard undefined) retain all of these unchanged.
- **Build system**:
  - Makefile: add ImGui sources to the PC build, exclude on `PLATFORM=switch`. Add `-DZ3R_NATIVE_SETTINGS_WINDOW=1` on PC.
  - MSBuild `.vcxproj`: add ImGui source files; the existing C++ toolchain handles them (ImGui is C++).
  - Switch Makefile (`src/platform/switch/Makefile`): no change required; the new flag stays off.
  - CI: existing Linux/macOS `make -j$(nproc) zelda3` continues to work with the additional sources.
- **Dependencies**: Dear ImGui is the only new external dep. Vendored, no system package required. Adds ~3 MB to the source tree and a small (~200 KB) increase in the stripped binary.
- **Determinism / seed reproducibility**: zero impact. Settings still serialize through the same `Settings_CanonicalSerialize` path; `settings_hash` is identical whether the values were entered in the in-game UI or the native window. The shared `Rando_GenerateSlot` is a pure relocation of the in-game generate body (the CLI path `MaybeRunGenerateSeedAndExit` is untouched), so the regression corpus stays green and there is **no `kGeneratorVersion` bump** (this is a UI change). The native "new random seed" button uses a UI-only `SplitMix64(SDL_GetPerformanceCounter())` entropy source — never the deterministic path; the seed is just an input.
- **Save format / sidecar / snapshot format**: unchanged. The native window's generate flow writes a sidecar randomizer slot via the same `Rando_GenerateSlot` the in-game screen uses (it does NOT `Placement_Install` — install remains slot-load-only); for preferences it writes only the sidecar `saves/rando_window.ini`, never `sram.dat`, `sram_rando.dat`, the snapshot stream, or the user's hand-edited `zelda3.ini`.
- **RAM-compare side-by-side mode**: unaffected — the native window does not run game code or write `g_ram`.
- **Race mode**: the native window's Spoiler/Placement viewer tab is hidden when the active slot is in race mode (same gate as the existing spoiler-suppression rule in `randomizer-save`).
- **Audit guard impact**: none — the audit guard scans game-code writes to `g_ram` cells, which this change does not introduce.

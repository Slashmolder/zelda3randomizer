# Design: Enemy/Boss Souls

## Context

Souls gate enemy/boss *existence* on item ownership. Research established these load-bearing facts about the current source (symbol anchors, verified 2026-07-05):

- **Spawn layers.** Static dungeon sprites materialize in `Dungeon_LoadSprites` → `Dungeon_LoadSingleSprite` (`src/sprite.c`), with the enemy-shuffle substitution `EnemyShuffle_PickDungeon(room, slot, vanilla_type)` called immediately before the sprite is created — the *final* species is known at that point. Overworld sprites two-stage through `Overworld_LoadSprites` (type table) + `Overworld_LoadProximaSpriteIfAlive` (lazy materialization). Dynamic spawns (overlords in `src/overlord.c`, boss parts, sprite-spawned sprites) all funnel through `Sprite_SpawnDynamically(Ex)` with hardcoded literal types and bypass enemy shuffle entirely.
- **Kill gates fire trivially on empty rooms.** `Sprite_CheckIfScreenIsClear` / `Sprite_CheckIfRoomIsClear` (`src/sprite.c`) test only *live* sprite slots (`sprite_state[i] != 0 && !(sprite_flags4[i] & 0x40)`). If gating enemies never spawn, `RoomTag_QuadrantTrigger` / `RoomTag_RoomTrigger` / `RoomTag_KillRoomBlock` / `RoomTag_GanonDoor` (`src/dungeon.c`) fire immediately. Nothing tracks "how many enemies should have been here." A held-shut design therefore needs an explicit rando-side hold.
- **Kill-state persistence is index-stable.** `sprite_where_in_room` bits are keyed by the sprite's *structural position* in the room's static data list (the load-loop `k`), not by live slot index — suppressing a subset of entries cannot corrupt other entries' persisted kill bits, provided the suppression path preserves the loop-counter conventions already used by the control-marker/overlord branches of `Dungeon_LoadSingleSprite`.
- **Boss shuffle is a whole-room redirect.** `BossShuffle_GetRenderRedirect`/`RenderHomeRoom` swap which room's sprite list loads; the assigned boss's own sprite IDs then flow through the normal static-load path. The per-seed assignment lives in the C static `g_boss_assignment[16]` (`src/rando/shuffle_boss.c`), already threaded into the logic VM as `PredicateContext.boss_assignment` consumed by `OP_CAN_KILL_BOSS` (`eval_can_kill_boss`, `src/rando/rando_logic.c`).
- **Logic is species-blind today.** `CanKillMostThings` and friends are firepower tests; no location or edge encodes "kill sprite X in room Y." Enemy shuffle is deliberately logic-neutral with a spec-level placement-digest invariant. The enemy-shuffle tables provide `kEnemyTable` (49 randomizable killable species), `kKillableRequiredRooms` (48 kill-clear rooms, currently advisory), and `kEsBossTypes` (20 boss/part IDs).
- **Item plumbing template = Triforce piece**: registry entry → generated `ITEM_*` id → `Rando_DispatchVanillaGrant` direct-write branch returning `kRandoLttpSkip` → confirmation cue + `kDirectGrantIcons` icon → `pool_add` under a settings gate → `is_progression_item()` classification → self-checks. `RandoCounts.by_item_id[256]` has headroom (150 used, ids 0-149; souls start at 150 and bring it to ~197).
- **Persistence budget is tight**: the 80-byte `RandoSlotHeader` and v3/v4 extension blocks are essentially full (one reserved byte left); the fork's convention for new save state is a new versioned extension block + a snapshot-tail TLV + a process-static live variable (`g_rando_boomerang_owned` pattern).
- **Settings budget**: `kSettingsCanonicalLen == 29`; bytes 25-27 are fully allocated, and byte 28 (appended by enemy-drop-sanity) uses only its low 2 bits for `enemy_drop_checks` — bits 2-7 of byte 28 are the free surface.
- **Enemy-drop-sanity exists (merged 2026-07-05, reconciled here)**: `enemy_drop_checks = Off/Keys/Dungeon/All` (`Settings_EffectiveEnemyDropChecks` coerces Dungeon/All→Keys under enemy shuffle, All→Dungeon under entrance shuffle, and `All × accessibility=locations` is refused pending temporal-location modeling of overworld stage windows). It adds `LOCTYPE_EnemyDrop = 18` (14 forced key drops incl. the HC Ball-and-chain guard big key, mirrored by the virtual item id 149 `HyruleCastleBigKey`) and `LOCTYPE_Enemy = 19` (~1234 ordinary checks; 13 boss/miniboss checks = the 10 dungeon bosses + the 3 GT refights, loc ids 1788-1800). Its generator `gen_enemy_check_tables.py` carries `source_type` (species) per check in the intermediate YAML and emits per-location kill predicates, but species does NOT survive into the runtime lookup headers — runtime granting keys on room + structural slot (`Rando_TryGrantEnemyCheck`), not species. Its kill predicates are species-blind firepower tests today; boss checks reuse `OP_CAN_KILL_BOSS`.

User decisions locked in: tiered setting (`off`/`bosses`/`bosses+enemies`); kill-gates stay shut without the soul; Agahnim and Ganon get souls.

## Goals / Non-Goals

**Goals:**
- Souls as first-class assumed-fill progression items; seeds are beatable-by-construction under any tier.
- Suppression covers all three spawn layers keyed on the final post-shuffle species.
- Kill-gated rooms hold their reward shut while soul-suppressed, without hard-softlocking the player.
- `souls_shuffle=off` is placement-digest-identical to current `main` (corpus-verified).
- Enemy shuffle's placement-digest-neutrality invariant is preserved.

**Non-Goals:**
- No per-seed *shuffling of which enemies exist* — souls gate presence, they don't relocate enemies.
- No exposure of per-room post-shuffle species to the logic VM (see D5 — deferred alternative).
- No vanilla pause-menu UI for soul ownership (tracker window + auto-tracker only, first iteration).
- No souls for non-enemy sprites (NPCs, traps, projectiles) or for killable one-offs outside the soul population — unlisted species always spawn.
- Switch in-game settings screen support (PC ImGui window is the settings surface per repo convention; Switch defaults to off).

## Decisions

### D1. Soul population and grouping

**Boss tier — 12 souls**: the 10 shuffleable/pinned dungeon bosses (Armos Knights, Lanmolas, Moldorm, Helmasaur King, Arrghus, Mothula, Blind, Kholdstare, Vitreous, Trinexx), **one** Agahnim Soul covering both encounters (`kBoss_Agahnim` and `kBoss_Agahnim2` are one character, same sprite `0x7A`; separate souls would be two near-identical progression checks), and a Ganon Soul.

**Enemy tier — one soul per curated family** (~25-35 souls), grouped from `kEnemyTable`'s 49 species by a hand-curated map committed inside the table generator (`assets/scripts/gen_enemy_shuffle_tables.py` or a sibling). Grouping merges palette/behavior variants (e.g. red/green soldiers → "Soldier Soul"). Rationale: the user picked grouped families; 49 individual souls would displace too much filler and make most souls redundant-feeling. The generator asserts every `kEnemyTable` species maps to exactly one family (completeness invariant, per the claim-grounding discipline: the generator IS the spec for this data).

**Fail-open for unlisted species**: any sprite ID with no soul mapping always spawns. This automatically excludes NPCs, traps, projectiles, cuccos, and killable one-offs from the feature without needing an exhaustive audit of all 256 IDs.

**Parts map to parents**: `{0x89→0x88 Mothula beam, 0x8D→0x8C Arrghus puff, 0xA3→0xA2 Kholdstare shell, 0xBE→0xBD Vitreous eye, 0xCC/0xCD→0xCB Trinexx arms}`. Room-data secondaries (Trinexx arms, Kholdstare shell) are suppressed alongside the parent (mirrors `BossShuffle_ShouldSuppressSecondary`); AI-spawned children need no handling — no parent, no spawn call.

### D2. Suppression architecture: one predicate, three hooks

A single query `Souls_SpriteAllowed(uint8 final_type)` (new `src/rando/souls.c`) — returns true unless souls active AND `kSoulForSprite[final_type]` is a valid soul AND that soul is un-owned. Called from:

1. **Static dungeon load** — in `Dungeon_LoadSprites` after `EnemyShuffle_PickDungeon` returns the final type. Suppression must preserve the structural-index bookkeeping: the entry still consumes its list position `k` (mimic the existing `0xe4`/overlord-marker branch return conventions) so `sprite_where_in_room` bits for later entries are unaffected. A suppressed entry increments a per-room-load counter (see D3).
2. **Overworld proximity load** — in `Overworld_LoadProximaSpriteIfAlive` (not at table build), so a soul obtained mid-area takes effect on the next proximity load without an area transition. The `overworld_sprite_was_loaded` per-block bit is NOT set for a suppressed spawn (the enemy was never there; it must appear once the soul is owned).
3. **Dynamic funnel** — at the top of `Sprite_SpawnDynamically(Ex)`, return the no-slot failure path when suppressed. This single hook covers overlord spawns, sprite-spawned sprites, and any boss-AI child spawns. Because the soul map contains only enemy/boss species IDs, item/effect/ancilla-ish sprites spawned through the same funnel are never suppressed — enforced by a selftest asserting the soul map is disjoint from known non-enemy spawn types.

**Boss rooms need no fourth hook**: with or without boss shuffle, the (possibly redirected) room's static list carries the assigned boss's sprite IDs through hook 1; keying on species makes suppression follow `boss_assignment` automatically.

**Mid-room acquisition**: suppression is evaluated at spawn time only; enemies appear on the next room/area (re)load. Documented player-visible behavior, not a bug.

**Alternative rejected**: hooking only `EnemyShuffle_Pick*` (misses all dynamic spawns — confirmed bypass) or spawning "inert ghost" sprites (touches damage/AI pipelines; far larger blast radius than a spawn veto — see the `Rando_PotBreakHook` suppress-enum precedent for a spawn-site veto).

### D3. Kill-gate hold semantics

`Dungeon_LoadSprites` counts soul-suppressed static entries into a live per-room counter (process-static, reset each room load). Rando-gated checks in `Sprite_CheckIfScreenIsClear` and `Sprite_CheckIfRoomIsClear` return "not clear" while the counter is nonzero. This holds shut every kill-gate consumer (`RoomTag_QuadrantTrigger`, `RoomTag_RoomTrigger`, `RoomTag_RekillableBoss`, `RoomTag_KillRoomBlock`) with two required refinements:

- **Escapability (REVISED during implementation)**: the original "skip trap-close actions" mitigation was based on a wrong model — shutters close unconditionally at room-header load (`dung_flag_trapdoors_down = 1` in the header loader; `DungeonTransition_Subtile_TriggerShutters` re-closes on subtile moves), and the kill tag only *opens* them, so "skipping the close" would leave every shutter open and collapse transit gating entirely. Shipped semantics: door behavior stays vanilla; a held room is exactly as escapable as a vanilla kill room whose enemies the current loadout cannot kill — walk-out through normal entry doors, Save-and-Quit for shutter entries (GT refights). Logic never routes through a held room without the souls, so the S&Q case only arises on off-logic dives, matching established ALTTPR practice.
- **`RoomTag_GanonDoor`** has its own any-active-sprite loop (not the shared clear checks) and gets its own hold, so a suppressed Ganon cannot open his own door prematurely.

**Alternative rejected**: letting gates open free (user decision) and per-tag bespoke guards (the clear-check chokepoint is two functions; per-tag guards invite drift).

### D4. Logic: boss souls via `boss_assignment`, room souls via generated static data

- **Boss/prize locations**: extend `eval_can_kill_boss` — when souls are active, AND `HAS_ITEM(kRandoBossSoulItem[boss])` into the existing per-boss kill predicate, where `boss` already resolves via `ctx->boss_assignment` (fallback `kRandoDungeonVanillaBoss`). A new generated table `kRandoBossSoulItem[12]` maps boss-pool index → soul item ID (Agahnim and Agahnim2 map to the same Agahnim Soul). This is dungeon-relative, so boss shuffle is followed with zero additional plumbing.
- **Souls-tier predicate**: new opcode `OP_SOULS_TIER_AT_LEAST <tier:u8>` reading the seed's settings from the predicate context (precedent: `OP_MODEWEAPONS_EQ`, `OP_GLITCH_LEVEL_AT_LEAST`). Logic YAML wraps soul requirements as `NeedsSoul(X) := NOT SOULS_TIER_AT_LEAST(t) OR HAS_ITEM(Soul_X)` macros so one logic blob serves all settings.
- **Kill-gated rooms (enemy tier) — AS BUILT (revised from the kKillableRequiredRooms sketch)**: the committed generator `assets/scripts/gen_soul_room_tables.py` derives the kill-gated set from ROOM-HEADER TAG BYTES (authoritative — `kKillableRequiredRooms` is an advisory Enemizer port, wrong for this purpose), classifies kill→doors (tags 0x01-0x0A) vs kill→chest (0x29-0x32) against the verified `kDungTagroutines` dispatch, reads resident soul sets from the room sprite lists, and computes what each room gates by FLOODING the committed vanilla door graph (`door_tables.gen.c`, DR-harvested): regions reachable from the dungeon's portals only through the room's trap-kind doors. Wrap surfaces: fork chest/boss/prize locations by id (`kDoorTblLocations`), the Aga1 event by name (curated region→site map), generated enemy-drop/enemy-check/pot-key locations by door-region, pot locations by room, and three reviewed cave bindings (Mimic Cave, Mini Moldorm Cave, Paradox Cave lower — trap-door presence asserted from the room-data door lists). Rooms with no enemy-souled residents are waived (soul-less species always spawn, and enemy shuffle substitutes only ESF_RANDOMIZABLE species, all souled); boss-soul rooms (GT refights) are excluded — the `CanKill<Boss>` macro terms on every gated location cover them (verified against 33_ganons_tower.yaml). Output `assets/rando/soul_rooms.gen.yaml` is gitignored with a **fail-closed guard**: `rando_logic_gen.py` bakes `kRandoSoulRoomsBaked` into logic_data.c and `BuildItemPool` refuses `bosses+enemies` seeds when it is 0 (the `chest_table.gen.bin` fail-open lesson). Logic-gen wrap-target misses are HARD errors, not warnings.
- **GT refights**: the Armos/Lanmolas/Moldorm refight rooms are outside the boss-shuffle room table (always vanilla species), so the GT climb gets static `NeedsSoul(ArmosKnights) AND NeedsSoul(Lanmolas) AND NeedsSoul(Moldorm)` requirements under the **boss** tier (boss species suppress at boss tier, so these gates bind even with enemy souls off).
- **Enemy-held keys with `enemy_drop_checks=off` — AS BUILT (runtime exemption, not logic terms)**: when drops are NOT itemized, the vanilla key model counts them as free in-dungeon keys at many sites (per-location HAS_AMOUNT thresholds, the wild-cap, the placer's nonpot free-grant, the door oracle) — soul-gating them in logic would mean surgery across the whole key model. Instead the static suppression hook EXEMPTS forced-drop source sprites (`Rando_SoulDropSourceExempt`, keyed on the vanilla (room, slot) against the drop lookup): the holder spawns souls-or-not, the key drops vanilla-style, and every free-key assumption stays true. When `enemy_drop_checks>=keys` the drop is a location whose predicate carries the holder's soul (generator term) and normal suppression applies. Player-visible rule: key-guards always stand their post unless their key is itemized.
- **Enemy-drop-sanity locations**: enemy-check (`LOCTYPE_Enemy`) and forced enemy-drop (`LOCTYPE_EnemyDrop`) locations require their source species' soul under the enemies tier. Implementation rides the existing generator: `gen_enemy_check_tables.py` already knows `source_type` per check and already emits per-location kill predicates — it gains a `NeedsSoul(soul_of(source_type))` term. The 13 boss/miniboss checks need no per-location work: the 10 boss checks resolve through the extended `OP_CAN_KILL_BOSS`, and the 3 GT refight checks take the same static refight soul gates as the GT climb. The virtual `HyruleCastleBigKey` derivation (id 149) follows its underlying forced-drop check's predicate, so Zelda's Cell / rescue logic inherits the guard's soul requirement automatically.
- **Goals**: Ganon-kill and Agahnim-kill predicates AND in their souls under souls tiers (Ganon Soul gates every Ganon-fight goal; Agahnim Soul gates Aga1-dependent DW access routes and Aga2).

### D5. Enemy-shuffle interaction: pin kill rooms and drop rooms, keep logic static

When `souls_shuffle == bosses+enemies` (EFFECTIVE) AND enemy shuffle is on, `EnemyShuffle_PickDungeon` returns the vanilla type for every room in the generated pin set `kRandoSoulPinRooms` — (a) kill-gated rooms with enemy-souled residents and (b) forced enemy-drop rooms, pinned WHOLE-ROOM rather than per-slot (as built: avoids the list-index vs runtime-slot convention mismatch between the picker's `es_slot` and the drop lookup's slot for zero real cost — 41 rooms). Soul requirements computed from vanilla species stay correct, and enemy shuffle's placement-digest-neutrality invariant survives (placement varies with the *souls* setting, never with the enemy-shuffle toggle). Non-pinned rooms shuffle freely; suppression keys on whatever final species results, and soul-less kill rooms stay soul-less (the picker substitutes only ESF_RANDOMIZABLE species, all of which carry souls — gen_soul_tables' completeness assertion). Precedent for coercing an axis to protect this invariant: `Settings_EffectiveEnemyDropChecks` already degrades Dungeon/All→Keys under enemy shuffle, which also means ordinary enemy-check locations and enemy shuffle never coexist — the only shuffled species that carry soul requirements are in the pinned rooms above.

**Door shuffle (added during implementation)**: `Settings_EffectiveSoulsShuffle` degrades souls to OFF (any tier) under door shuffle — the door oracle is species-blind (counts enemy-held keys and floods shutters with no soul model), the generated kill-room requirements are vanilla-door-graph-specific, and empirically even the BOSSES tier's soul-gated boss/prize predicates made the door-layout fill exhaust its whole attempt budget per layout candidate (souls=all + door_basic timed out across 7 layout passes × 256 attempts under the conservative fill). Pool, VM, placer gate, runtime, hash all read the effective value; a settings-selfcheck asserts the degrade.

**Alternative rejected (for now)**: exposing per-room post-shuffle species to the VM (`PredicateContext.enemy_room_assignment` + install-before-placement ordering change). Strictly more chaotic and preserves full shuffle freedom, but it breaks the digest-neutrality invariant, requires reordering `rando_generate.c`, and multiplies the audit surface. Documented as a future extension.

### D6. Settings encoding: canonical byte 28, bits 2-3

`souls_shuffle` (3 values, 2 bits) rides in byte 28 — the byte enemy-drop-sanity appended when it grew `kSettingsCanonicalLen` to 29 — whose low 2 bits hold `enemy_drop_checks`, leaving bits 2-7 free. No length grow, no serializer cascade; default 0 preserves the byte-identical default settings hash. (Earlier drafts targeted "byte 25 bits 6-7"; byte 25 is the packed entrance/chains axis byte with only bit 7 free — a single bit, too small for a 3-value axis. Free surfaces post-merge: byte 25 bit 7, and byte 28 bits 2-7.) CSV key `souls_shuffle=off|bosses|all` via `Settings_ParseCsv`; ImGui `EnumCombo` in the settings window; `apply_derived_rules` needs no coercions identified so far (souls compose with every world state; hunt goals keep the existing `accessibility=none` convention), though Standard × enemies tier is a watch item (see Risks).

### D7. Persistence: sidecar v5 + snapshot TLV + process-static

`uint8 g_rando_soul_flags[8]` (64-bit bitfield; ~47 bits used) as a process-static live array. Persisted via (a) a new v5 sidecar extension block (8 bytes + reserved padding) appended per the v3→v4 precedent with format-version gating in `RandoSave_ReadFile`/`WriteFile`, and (b) a new snapshot-tail TLV type for the M4 cold-replay path (mirrors `TAIL_DOOR_LAYOUT`). Old saves/sidecars read as zero souls owned — safe default (nothing spawns that shouldn't; seeds generated with souls off never read the field). Bit index = soul item ID − first soul ID (stable because the registry is append-only).

### D8. Item family plumbing (Triforce-piece template)

Registry entries (`category: soul`, `dispatch: soul_direct_grant`); one `Rando_DispatchVanillaGrant` branch: set bit, return `kRandoLttpSkip` (confirmation cue via `Rando_ReceiveOrConfirm`, no receipt animation). Names auto via generated `Rando_GetItemName`. Art: **one generic soul icon** cell appended to `custom_item_gfx.png` (`kRandoCustomGfx_Soul`), shared by all souls through `direct_grant_icons.yaml` (optionally a second cell to distinguish boss vs enemy souls) — 30+ bespoke 16×16 tiles is not worth the pixel-art cost for v1. Pool: `pool_add` per soul gated on tier (bosses: 12; +enemies: +family count); `is_progression_item()` includes the soul ID range. Field-item draw resolution flows through the shared resolver so ground/pot spawns render the soul icon (per the draw-must-mirror-grant rule).

### D9. Placement and accessibility

Souls are ordinary assumed-fill progression items — the algorithm's assume-unplaced discipline already prevents a soul from landing behind its own gate (placing Soul_X removes it from the assumed set, making X-gated locations unreachable for it). Two review points, not new mechanisms: (a) `Goal_IsCompletable`'s GT-crystal circularity special-casing is re-read against soul-gated boss kills; (b) souls raise the progression-item count by up to ~47, so restrictive combos (Retro + hunt + strict accessibility) get corpus coverage to characterize refusal rates.

### D10. Placer: enemies-tier fill model + tier-aligned attempt acceptance (added during enemy-tier implementation)

The kill-room wraps collapsed the pre-souls fill on enemies-tier seeds (121-171 unreachable placements in the best of 256 attempts; a soul even landed on a location requiring itself via the reachability-ignoring forward-fill). Root causes, both fill-GUIDANCE issues — the per-attempt sphere-walk validation is and remains the soundness arbiter, so neither model can ship an unsound seed:

1. **Placed pool items vanished from per-turn reachability** (assumed-unplaced-only) — a placed soul permanently killed its gated cluster for the rest of the fill.
2. **Pins were phantom grants** — prize/event/TakeAny/customizer pins were seeded unconditionally into the assumed counts, so GT-entry certified open via crystals whose Prize locations were themselves soul-blocked (instrumented: `TRBoss108=0` while GT entry evaluated reachable), and every attempt failed validation.

**As-built: the fill model is TIER-SCOPED.** Seeds with EFFECTIVE `souls_shuffle=all` use `compute_reachability_collecting_placed`: per turn, reachability = assumed(unplaced) + a fix-point collection of committed items/pins whose locations are reachable (the upstream `RandomAssumed` "fix-point reachability expansion" contract), with placed copies of the currently-placed item id excluded (a key must never sit in a slot justified by its own placed siblings). Every other seed keeps the pre-souls conservative model unchanged. The scoping is a bisected calibration fact, not a hedge: applying the collection model globally degraded the calibrated key-threshold fills — full collection deep-stacked dungeon keys on `pot_shuffle=all` (674 unreachable), and under door shuffle both collected keys (oracle source double-count) and honest-pin prize derivation churned `pot × door` into 256-attempt fallback-quality fills. The worst-case key models (pot depths, door oracle) and the conservative fill are co-designed; the enemies tier (which forces vanilla doors via the `Settings_EffectiveSoulsShuffle` degrade) composes with the collection model.

**Attempt acceptance is tier-aligned globally**: an attempt is accepted when it meets the seed's effective-accessibility bar (locations → all placements reachable; items → all progression reachable; none → goal completable) plus zero forward-fill fallbacks and the Standard escape weapon/lamp constraints — instead of unconditional full reach, which is unattainable for combos with modeling-stranded junk (wild keys × dungeon enemy checks permanently strand a fixed 63 junk-holding checks, pre-existing) and burned the whole attempt budget (~2m45s) on seeds whose attempt 0 already satisfied the real acceptance gate (0.8s after, same digest). Side effect: `check_placer_determinism.py`'s retry-exhausting canary no longer exhausts (warns, still passes) — retune it when a reliably-exhausting combo is known.

All changes are deterministic (no RNG in collection; order-independent passes). Corpus digests move only for enemies-tier seeds and previously-attempt-exhausting combos; kGeneratorVersion 129.

### D11. Fresh-eyes review outcomes (task 6.5, four parallel reviewers)

Fixed from findings: **(a) dungeon-chains seam gating** — the factored `<D>_BossRoom` approach edge (built before the soul wraps, with `CanKillBoss` deliberately stripped) is what chains redirect the successor dungeon's entry through, so the placer could certify the successor while the previous dungeon was soul-held or its boss unkillable (a PRE-EXISTING chains gap the souls terms made acute). The edge now carries `CanKillBoss(D)` plus the same kill-room soul terms as the dungeon's Boss location — logically inert off-chains (Boss/Prize already required both). **(b)** Attempt accept additionally requires `Goal_IsCompletable` at every tier (belt-and-suspenders; reachability already implies it today). **(c)** Room `0xFF` (door-table no-room sentinel) excluded from `room_wraps`. **(d)** Generator asserts boss HOME rooms (parsed from `kBossRooms`) never contain enemy-soul residents — a suppressed bystander would hold the boss-death prize spawn shut; true today, now fail-closed. **(e)** Region-wrap zero-hit drift warning in the logic-gen join. **(f)** Spec corrected: auto-tracker soul exposure is DEFERRED (souls live outside `g_ram`), not shipped. Documentation comments added at `RoomTag_Agahnim` (state-bit-driven, needs no hold) and `RoomTag_KillRoomBlock` (held through the clear check).

Reviewer claims rejected against evidence: the items-tier accept bar "misses goal events" is unreachable today (prizes are progression placements; full inventory opens the goal events — hardened anyway per (b)); the own-id exclusion "under-collects sibling keys" is the documented, intended conservatism; narrowing the collection model to soul-item turns would reintroduce the phantom-cluster collapse.

**Post-review perf regression + fix (found by the final corpus green-check).** Fixes (a)+(b) together slowed the two slowest door-layout corpus entries (seed `0xD004`, already brushing the budget pre-review) past the 60s runner budget (85.7s measured): the predicate VM evaluated EVERY AND/OR child to advance its cursor (no length prefixes), so the seam fix's `CanKillBoss(D)` on 13 always-present factored edges was re-evaluated in every reachability fix-point of every attempt even where logically inert, and (b) eagerly re-ran `Goal_IsCompletable` (a full fix-point) on bar-passing-but-doomed attempts. Fixed by (1) reordering the accept bar so `Goal_IsCompletable` is the last conjunct (short-circuit order cannot change the ANDed accept set — digest-inert) and (2) real short-circuit evaluation in the VM via a structural `skip_pred` walker, validated by a new `Logic_SelfCheck` block that walks every predicate blob in all generated tables asserting exact-length consumption (a future op wired into `eval()` but not `skip_pred` fails the selfcheck immediately). Net: the slow entries now run ~55s — FASTER than pre-review — while keeping both soundness fixes; full-corpus digest identity on both compilers re-proves behavior-neutrality (`kGeneratorVersion` unchanged per the inert-change exception). The corpus scripts' per-entry budget was raised 60s→120s: legitimate hard door seeds sit near 55s, and the 60s cap made them flake under CI/machine contention (two separate false alarms this session).

## Risks / Trade-offs

- **[Kill-room escapability]** Some tag handlers may close doors before the hold is consulted, trapping the player in an empty room. → Enumerate close actions in the four kill-tag handlers during implementation; requirement is exit-without-S&Q; playtest sweep across representative kill rooms (incl. trapdoor and shutter variants).
- **[Cutscene chains waiting on suppressed sprites]** Ganon's pyramid drop-in, Agahnim's tower sequence, and boss-intro choreography may freeze if the awaited sprite never spawns (known corollary: a freeze in a prize/cutscene sequence is usually an un-spawned awaited object). → Playtest the Aga1, Aga2→Ganon, and each boss-room entry with the soul missing; prefer "room is simply empty and walkable" as the observable behavior. Ganon's exact spawn call site is UNVERIFIED — first implementation task confirms whether it flows through `Sprite_SpawnDynamically` (hook 3) or room data (hook 1).
- **[Over-suppression through the dynamic funnel]** `Sprite_SpawnDynamically` also spawns non-enemy sprites. → Soul map contains only enemy/boss species; selftest asserts disjointness with a curated non-enemy spawn-type list; fresh-eyes audit greps every `Sprite_SpawnDynamically` call site.
- **[Generated table fail modes]** Room→species table generated from gitignored asset data can silently regress in fresh worktrees. → Fail-closed generation when the enemy tier is active + CI guard (pattern: `check_no_embedded_data` / codegen-wiring checks); `setup_worktree.py` mirrors the new artifacts.
- **[Pool pressure / refusal rates]** ~47 extra progression items tighten fills on Retro/hunt/strict-accessibility combos. → Corpus entries per tier × representative world states; judge refusals by spoiler-write (existing convention); consider derived-rule coercion only if corpus shows pathological refusal rates.

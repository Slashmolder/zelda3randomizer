# randomizer-save — delta for add-rando-grass-rock-shuffle

## ADDED Requirements

### Requirement: Terrain registry activation guard (slot extension v8)

The sidecar SHALL grow by a new format version (file `format_version` 8) that (a) appends `terrain_registry_digest` (u32 LE) and `terrain_registry_count` (u16 LE) plus a `terrain_registry_present` (u8) to the per-slot extension block (ext size 37 → 44 bytes; the three fields occupy @37-43), written on every randomizer-slot save from the binary's compiled-in generated terrain registry and mirroring the existing pot registry guard fields (`pot_registry_digest`/`pot_registry_count`, as-built in the v4 extension block per `rando_save.h`), and (b) widens the per-slot canonical settings blob to the new `kSettingsCanonicalLen` (30 bytes, for the appended terrain canonical byte [29]), mirroring how format_version 4 widened it to 29 — shorter blobs from older files zero-extend on load, so pre-v8 slots read both terrain axes as `off`. At slot activation, a slot whose stored canonical settings have `grass_shuffle` or `rock_shuffle` non-off SHALL be refused — with a visible message, never a silent fallback to vanilla drops — when the running binary's terrain registry digest or count does not match the slot's stored values, or when the slot predates the v8 extension (guard fields absent ⇒ treated as a mismatch for terrain-active settings), or when the binary's generated terrain registry is empty/missing. Slots with both axes off SHALL ignore the guard fields entirely. Cross-version compatibility follows the existing contract, which gates in BOTH directions (the reader derives the slot-ext and settings-blob sizes from the file's `format_version`, so older binaries cannot skip sections they don't know): a v8-writing binary reads v1..v7 files with their shorter bodies, but a pre-v8 binary refuses a v8 file outright — the first v8 write therefore makes the whole sidecar (including terrain-off slots) unreadable to older binaries, exactly as prior format bumps did. This downgrade implication is accepted and inherent to the format's sequential slot layout.

#### Scenario: Empty-registry binary refuses a terrain slot
- **WHEN** a binary built without the generated terrain registry (fresh worktree, artifacts not mirrored) activates a slot whose settings have `grass_shuffle = all`
- **THEN** activation is refused with a message naming the terrain registry mismatch; no gameplay starts with terrain checks silently resolving to vanilla drops

#### Scenario: Registry drift across builds is caught
- **WHEN** a slot was generated by a binary with terrain registry digest X and is loaded by a binary whose regenerated registry has digest Y ≠ X
- **THEN** activation is refused (placement location ids would rebind across the renumbered registry), matching the pot-registry and door-digest hard-fail behavior

#### Scenario: Terrain-off slots are unaffected by the guard
- **WHEN** a slot with `grass_shuffle = off` and `rock_shuffle = off` is loaded by any binary, including one with no terrain registry at all
- **THEN** the slot activates normally; the guard fields are not consulted

#### Scenario: v7 sidecar files still load
- **WHEN** a `format_version` 7 sidecar (37-byte ext block, 29-byte settings blob, no terrain fields) is read by a v8-writing binary
- **THEN** the file loads through format-version gating; the 29-byte settings blob zero-extends to 30 so both terrain axes read `off` and the guard is not consulted; the next write upgrades the file to v8

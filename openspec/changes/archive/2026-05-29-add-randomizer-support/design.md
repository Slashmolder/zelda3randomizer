## Context

This repository is `snesrev/zelda3` — a C reimplementation of *A Link to the Past* that uses a fixed-layout 128 KB `g_ram[]` buffer mirroring SNES RAM. Every game variable lives at a known offset, exposed via macros in `src/variables.h`. The recently merged BPS support (commit `fbbb3f9`) shows the project is already moving toward patched-content workflows.

The community-standard randomizer, **ALTTPR** (Berserker/VT fork), is a JavaScript/PHP service that takes a seed string + settings and produces a patched ROM. Its placement algorithm is well-documented: a logic graph over ~216 item locations, an item pool of ~216 items (after junk-padding), and an "assumed fill" placement pass with retry on dead-ends. Logic predicates compose item-presence, item-amount, world-state, goal, dungeon-flag, and trick checks; difficulty modes (Normal/Hard/Expert/Insane) modify predicates per location.

Four facts about this port shape the design:

1. **All game state is in `g_ram[]`.** Items are byte locations at `0xF340+`. This makes a *placement override* layer cheap: intercept the moment the game decides "grant item X to Link," and redirect via a placement table indexed by location ID.

2. **The dual-runtime / RAM-compare model.** When the original ROM is supplied as argv[1], every frame's `g_ram` is diffed against the emulated 65816. Any divergence in vanilla mode is a bug. Randomizer mode must therefore be opt-in and explicitly disable RAM-compare when active.

3. **Saves are one monolithic 8 KB SRAM image with 3 slots + a backup region.** Per [select_file.c:43](src/select_file.c:43) and [messaging.c:259-266](src/messaging.c:259), `saves/sram.dat` is a single 8 KB buffer; `kSrmOffsets[4] = {0, 0x500, 0xa00, 0xf00}` is *not* four slots — it is three slots at 0/0x500/0xa00 *and a backup region base at 0xf00*. `SaveGameFile` writes each slot to both `offs` and `offs + 0xf00`. Layout: slot 0 primary 0x0000-0x04ff + backup 0x0f00-0x13ff; slot 1 primary 0x0500-0x09ff + backup 0x1400-0x18ff; slot 2 primary 0x0a00-0x0eff + backup 0x1900-0x1dff; unused 0x1e00-0x1fff (512 bytes). There is no per-slot file and no room for a 4th slot. Randomizer state lives in a sidecar file; the file-select kind-toggle pivots on this constraint.

4. **The game has no text-input infrastructure.** Input is filtered joypad/keybind state in `main.c`/`config.c`. No SDL_TEXTINPUT, no software keyboard, no IME hook. Share-string entry needs new plumbing.

5. **Save snapshots are NOT a raw `g_ram` dump.** Per [zelda_rtl.c:533-558](src/zelda_rtl.c:533), `StateRecorder_Save` writes an 8-uint32 header + an input log + an optional `base_snapshot` + a fresh `SaveSnesState` dump. Load (`StateRecorder_Load`) seeks past header → log → base_snapshot → SnesState dump and stops. Reloading in replay mode either calls `LoadSnesState` on the base_snapshot or `ZeldaReset(false)` then replays input from frame 0. Any randomizer-state persistence on the snapshot must respect this model — appending bytes after the SnesState dump is what older readers will silently skip; the SnesState dump itself captures `g_ram` so the `kRam_Rando*` cells survive.

Stakeholders: ALTTPR runners (want a reproducible regression corpus and competent logic), casual rando players (want presets and trackers), and existing vanilla players (must not regress).

## Goals / Non-Goals

**Goals:**

- Generation is deterministic across Linux/macOS/Windows/Switch given `(generator_version, settings, seed_u64)`, validated by a regression corpus in CI.
- All randomization happens in-process — no external service, no separate web tool, no shell-out.
- Vanilla play and RAM-compare verification remain fully unaffected when no randomizer slot is active.
- One dispatch function (`Rando_OnLocationCheck(location_id, vanilla_item_id)`) per grant site; no rewriting of game logic.
- Logic is YAML-driven, compiled to a typed VM at build time. Hand-written C predicates are prohibited.
- Phased delivery — Phase A ships item shuffle with all four world-state modes and the standard goals, with three logic axes pinned: `tricks=none`, `item_pool_difficulty` all four values supported (easy/normal/hard/expert), `logic=NoGlitches`.
- Player can upgrade the binary mid-playthrough without losing access to their seed. (Saves embed the placement table, not just a digest.)

**Non-Goals:**

- **Cross-compatibility with alttpr.com share strings or spoiler JSON.** Two implementations of two different RNGs will draw different placements for the same seed; pretending otherwise misleads racers. Our share strings are explicit about being ours (magic-prefixed) and never decode an alttpr.com hash.
- **Bit-identical-to-ALTTPR placements.** Earlier drafts claimed this; it is impossible while keeping an independent RNG. The actual validation target is our **own** regression corpus, generated by us, pinned per generator-version.
- **Multiworld** (cross-game item shuffle). Out of scope. The dispatcher is intentionally pull-only (`OnLocationCheck`); a multiworld push API (e.g. `Rando_GrantItem(item, source)` with a frame-safe queue) would be additive and is left to a future change. This change does not pre-architect for it.
- **Door Randomizer**. Out of scope; requires dungeon-layout regeneration beyond the placement-override model.
- **Cosmetic-only shuffles** (sprite/palette/music). Scoped to Phase D, not Phase A.
- **Trick and hard/expert logic** (boots-clip, fake-flipper, dark-room navigation, etc.). Scoped to Phase B+ via additional VM ops and YAML predicates.

## Decisions

### D1. Placement layer as runtime override, not asset rewrite

Two options:
- **(a) Rewrite assets per seed**: regenerate `zelda3_assets.dat` chest/NPC tables. ALTTPR does this.
- **(b) Runtime override**: keep assets vanilla; intercept at the grant site and consult a placement table by location ID. ← **chosen**.

(b) needs zero asset-pipeline changes, generates in well under a second, and produces a clean diff vs. vanilla in the C code (one `if (rando_active)` per grant site). (a) would force a re-pack on every regeneration and fight the existing asset cache.

**Customizer foothold** (ALTTPR's "customizer" — where the user pre-pins specific items to specific locations and the filler fills around them, deferred to Phase C/D): the dispatcher API `Rando_OnLocationCheck(location_id, vanilla_item_id) → substitute_item` is identical for a generator-produced placement table and a fully-user-pinned one. The dispatcher does not care how the table was produced. The customizer fits into this design without VM or dispatcher changes; only the settings-screen UI gains a placement-pinning surface. Confirming this now so a future customizer change doesn't require dispatcher rework.

### D2. Logic engine = static graph compiled at build time + bytecode predicate VM

Locations, regions, entrances, and predicates are described in `assets/rando/logic.yaml`. A build-time tool (`assets/rando_logic_gen.py`) parses it and emits `src/rando/logic_data.c` with `LocationDef[]`, `RegionDef[]`, `EdgeDef[]`, and bytecode predicate streams.

**Predicate VM op set** (Phase A):

- `OP_HAS_ITEM <item_id>` — boolean presence
- `OP_HAS_AMOUNT <item_id> <n>` — count comparison (≥) over a single item ID
- `OP_HAS_ANY_OF <item_id_list>` — at least one of (sword 1/2/3/4, glove/mitt, bottle 1..4)
- `OP_HAS_ANY_COUNT <item_id_list> <n>` — total count over the union of distinct IDs ≥ n. Required for predicates like "has ≥ 2 bottles total (any contents)" (with bottle-with-contents modeled as distinct item IDs per `randomizer-core` spec), "has ≥ 10 hearts total" (combining heart pieces, heart containers, and starting hearts), and "has ≥ 2 swords if absolute-sword mode". These predicates appear in normal-difficulty logic, not just trick logic, so the op is Phase A.
- `OP_WORLDSTATE_EQ <state>` — Open/Standard/Inverted/Retro
- `OP_GOAL_EQ <goal>` — current goal
- `OP_GOAL_REQUIRES_DUNGEON <dungeon_id>` — true if the active goal requires clearing this dungeon
- `OP_DUNGEON_CLEARED <dungeon_id>` — boss defeated flag
- `OP_REGION_REACHABLE <region_id>` — recursive reference (memoized per fixed-point iteration; consults the `RegionRemap` overlay before traversing static edges)
- `OP_HAS_PRIZE <prize_id>` — true iff the dungeon to which prize shuffle assigned that prize is cleared
- `OP_MEDALLION_OPENS <entrance_id>` — true iff the inventory contains the medallion that medallion shuffle assigned to this entrance
- `OP_AND`, `OP_OR`, `OP_NOT` — composition

**Reserved for Phase B+**:

- `OP_TRICK <trick_id>` — true if the trick is enabled in current settings (e.g., `Trick_BootsClipThievesTown`, `Trick_FakeFlipper`, `Trick_DarkRoomNav`)
- `OP_DIFFICULTY_AT_LEAST <level>` — pool difficulty already in Phase A (see Goals/Non-Goals); this op is for predicates that *gate* on difficulty (e.g., trick logic that needs hard-pool item availability)
- `OP_GLITCH_LEVEL_AT_LEAST <level>` — no-glitch/overworld-glitch/major-glitch

**Per-seed runtime data (NOT compiled into `logic_data.c`)**:

`OP_REGION_REACHABLE` consults a static graph in `RegionDef[]`/`EdgeDef[]`. Phase C entrance shuffle (Phase C) needs per-seed region remapping — interior X connecting to entrance Y. To keep the VM unchanged across phases, the design adds a runtime overlay `RegionRemap[entrance_id] → interior_id` consulted by `OP_REGION_REACHABLE` before traversing static edges. Phase A's overlay is the identity map (no remapping). Phase C swaps in a non-identity overlay generated by the entrance-shuffle module. This is called out now so the data model is forward-compatible.

The YAML grammar is a proper expression language with parens, precedence, named predicate macros (e.g., `CanReachAgahnimTower`), and references — not raw literals. The generator validates references and forbids cycles in non-`OP_REGION_REACHABLE` paths. The VM core (excluding op handlers) is small; with all ops handled the C size is on the order of 200-400 lines, not 50. Earlier draft's "50 lines" was wrong.

### D3. Determinism contract

A seed is fully reproducible from `share_string = base32(magic[4] | generator_version[2] | settings_hash[16] | seed_u64[8] | checksum[2])`.

To guarantee cross-platform determinism, the generator module SHALL NOT use:
- `rand()`, `random()`, `arc4random()`, or any non-vendored RNG
- `time()`, `clock_gettime()`, or any wall-clock or monotonic time
- Uninitialized memory reads
- Iteration over hashed containers without an explicit stable sort
- Floating-point arithmetic for any decision-affecting computation

The generator is built with these guarantees enforced (1) by code review during the audit, and (2) by a CI job that runs the regression corpus on every supported platform and asserts byte-identical placement digests.

### D4. RNG choice — xoshiro256\*\*

xoshiro256\*\* is chosen for the rando generator: simpler implementation, comparable statistical quality to alternatives, small state, deterministic seeding from a `seed_u64` for cross-platform reproducibility.

**Why this is fundamentally different from ALTTPR** (verified by reading `alttp_vt_randomizer/`):

PHP's *built-in* `rand()` / `mt_rand()` are Mersenne Twister. ALTTPR could have used them seedably for reproducibility, but **it doesn't**:

- ALTTPR's `app/Helpers/number.php:11-13` defines `get_random_int()` as a wrapper around PHP's `random_int()`, which is **CSPRNG** (`/dev/urandom` / `BCryptGenRandom` / `arc4random`) — not Mersenne Twister. CSPRNG is not seedable.
- `app/Filler/RandomAssumed.php`, `app/Randomizer.php`, `app/Support/Collection.php` use only `get_random_int()`. Zero `mt_rand` / `mt_srand` calls in the codebase.
- `app/EntranceRandomizer.php:10` has a stale comment saying "We use mt_rand as it is much faster than rand" — but the actual `randomize()` method shells out to a Python process (`vendor/z3/entrancerandomizer/EntranceRandomizer.py`) with the `--securerandom` flag. The mt_rand comment is dead documentation; grep confirms zero actual mt_rand calls.

**ALTTPR's "reproducibility" comes from database storage, not seeded determinism.** `app/Seed.php` is an Eloquent database model:
```php
class Seed extends Model {
    public static function boot() {
        $hasher = new Hashids('vt', 10);
        static::created(function ($seed) use ($hasher) {
            $seed->hash = $hasher->encode($seed->id);  // hash = encoded DB primary key
        });
    }
}
```

The "seed hash" the user sees is a Hashids-encoded database primary key. ALTTPR's reproducibility flow: generate via CSPRNG → store placement in DB row → return Hashids of the row ID. To "reproduce" later: look up the row by hash → return the stored placement. ALTTPR has no seeded-deterministic generation; the "seed" is a DB lookup key, not an RNG seed.

**Our model is the inverse**: no database, no central server. Same `(generator_version, settings, seed_u64)` reproduces exactly across platforms via xoshiro256\*\*. Our share strings encode the inputs to a deterministic regeneration; ALTTPR's hashes encode a database row ID. The models are not bridgeable — we cannot decode alttpr.com hashes (we have no access to their DB) and they cannot decode ours (their model has no concept of "regenerate from settings+seed").

Implication: alttpr.com share strings will not decode (different format, different model); our share strings will not work on alttpr.com. The settings screen detects ALTTPR hash format and surfaces a clear error.

### D5. Regression corpus, not parity corpus

`tests/rando_corpus/` ships (settings, seed_u64) → expected-placement-digest pairs. Initial corpus: 50 seeds across world-state × goal × item-pool-difficulty. Corpus is **generated by us** from a pinned `generator_version`; advancing the version regenerates the corpus and bumps the manifest. This is a regression guard, not an ALTTPR-parity check. The corpus README documents the generator version it was generated from.

ALTTPR is referenced for logic *content* (the logic graph YAML mirrors ALTTPR's logic semantics for the in-scope subset) but not for byte-level placement output. We cannot validate ALTTPR-equivalence beyond "solvability under the same logic" because of the RNG choice.

### D6. Save storage — sidecar file with embedded placement table

`saves/sram_rando.dat` is a sidecar file parallel to `sram.dat`. Layout:

```
[ file_header (16 bytes): magic, format_version, slot_count, file_crc ]
[ slot_0 (variable) ]
[ slot_1 (variable) ]
[ slot_2 (variable) ]
```

Each slot (authoritative layout — see `randomizer-save` spec):

```
[ slot_header (64 bytes):
    magic[4], slot_kind (Empty|Vanilla|Randomizer), generator_version,
    settings_hash[16], share_string[32] (raw binary form),
    last_vanilla_write_version, sram_slot_checksum_at_last_write,
    placement_table_size (uint16), flags, reserved ]
[ placement_table (placement_table_size bytes): full per-location item assignment ]
[ checked_location_bitmap ((placement_table_size/2 + 7) >> 3 bytes,
    sized so it can hold one bit per registry location):
    Phase A baseline is 27 bytes for ~212 locations; sized by formula for forward-compat ]
```

The spoiler file path is **not** stored in the slot — it is derived at runtime from `[randomizer] spoiler_dir` config + the slot's `share_string`. An earlier draft of this section listed a `spoiler_path[64]` field; it has been removed in favor of the runtime-derive approach (see `randomizer-save` spec).

The placement table is **embedded in full**, not just digested. This is the critical fix that removes the "upgrade breaks saves" UX disaster: a player on v1.0 starts a seed, v1.1 ships a logic-graph fix, the player upgrades — and their save still loads because we don't need to regenerate to find out what's where, we just read the embedded table. The new binary's logic graph may *describe* locations differently (e.g., tighter requirements), but the player's existing placement is still playable to completion as it was.

`generator_version` mismatch on load surfaces a warning (logic semantics may have shifted) but does not refuse the load. Settings-hash drift is similarly informational.

Sizing: 80-byte slot header + ~424-byte placement table (~212 × uint16 baseline; varies by world-state) + ~27-byte bitmap ≈ ~531 bytes per slot. Total sidecar file ≈ 16 (file header) + 3 × ~531 ≈ 1.6 KB for 3 slots. The "2 KB-is-too-much" rejection from an earlier draft is reversed; storage is trivial. Exact per-slot size is recorded in `placement_table_size`; `Retro` slots are larger because Retro adds shop locations.

Vanilla `sram.dat` is byte-untouched. Vanilla saves load identically to before, with the sidecar file simply absent for vanilla slots.

### D7. Feature-flag gating with strict init order

`features.h` gains `kFeatures1_*` and a `kRam_Features1` cell, plus `kRam_RandoSlotActive`, `kRam_RandoStartingInventoryGranted`, `kRam_RandoSettingsHashLo/Hi`. The runtime checks the master flag at every dispatch:

```c
if (enhanced_features1 & kFeatures1_RandomizerActive) {
    Rando_OnLocationCheck(location_id, vanilla_item_id);
} else {
    // vanilla path unchanged
}
```

**Strict init-order rule**: every new `kRam_*` cell SHALL be initialized to a known value in `ZeldaInit` (or the loader path) before *any* game code can read it. The CI test runs the per-chapter replay savestates under the new binary in vanilla mode and asserts that `g_ram` at every newly-added offset matches the pre-change byte pattern. If a vanilla replay observes a new cell at a different value than vanilla-baseline, the build fails.

### D8. UI integration — kind-toggle on 3 slots, NOT a 4th entry

An earlier draft proposed adding a 4th "RANDOMIZER" entry to the file-select screen. **This is unimplementable**: the 8 KB `sram.dat` has only ~512 unused bytes (3 slots × {primary, backup} = 7.5 KB; per the analysis in Context fact 3). There is no room for a 4th SRAM slot, and the sidecar file alone cannot host a "fourth" slot because the file-select screen still needs to read vanilla shadow state from `sram.dat` for the slot, which doesn't exist.

**Chosen approach**: Each of the existing three save slots gains a *kind* field (vanilla or randomizer) stored in the sidecar file. The file-select screen reads each slot's kind and renders the appropriate banner:

- Slot kind = **vanilla** → existing vanilla banner (name, sword/shield/heart icons).
- Slot kind = **randomizer** → rando banner (truncated share string, world-state abbrev, goal abbrev, "R" badge).
- Slot kind = **empty** → "NEW GAME" prompt; on confirm, ask kind (vanilla / new randomizer / load share string).

Erasing a slot resets its kind to empty and removes its sidecar entry. Copy is supported only between same-kind slots (vanilla→vanilla or rando→rando), or refuses with a clear error. This pivot avoids file-select geometry surgery: `kSelectFile_Draw_Y[3]` and the 3-slot OAM offsets are preserved, only the per-slot rendering function dispatches on kind.

### D8a. Asset-data integrity — warn-not-block (revised from earlier hard-block)

An earlier draft refused to start a rando slot if any byte of the loaded asset blob differed from a vanilla baseline. Most users of this port have sprite packs, palette mods, MSU-1 music packs, or community translations — they're who the port exists for. A hard-block would lock out the entire audience for the sake of a placement-safety property they rarely actually care about (cosmetic mods don't affect placement).

**Phase A behavior**: compute `SHA-256(asset_blob)` after `LoadAssets()` returns; store in `g_assets_hash`. Compare to `kVanillaAssetsHash` baked by `restool.py` codegen at build time. On mismatch, the settings screen's first generation attempt with that asset blob surfaces a dialog explaining the risk (cosmetic-only mods are safe; chest/NPC table mods may misbehave) with three choices: **Always allow** (persists `(asset_hash → allow)` in `zelda3.ini` `[randomizer]` `asset_hash_decisions = ...`), **Allow once** (in-memory only), **Cancel**. The decision is keyed by hash so the dialog won't reappear for the same asset blob.

**Phase B refinement**: a *subset* hash computed by `restool.py` over only the asset blobs the placement layer actually depends on (chest-content tables, NPC-gift IDs, item-byte tables, location-flag offsets). Cosmetic blobs (palettes, sprite GFX, music samples) are excluded. With subset-hash in place, the warning fires only when the user has actually modified placement-relevant data, which is a vastly smaller set.

Implementation: `g_assets_hash` is the full-blob hash in Phase A; the subset-hash is added in Phase B without changing the warning UI.

### D9. Tracker overlays as `hud.c` extensions with inventory-change triggers

The item-grid tracker re-renders only when reachability state changes (cheap: track `reachability_state_counter` per §D13 and bump on dispatcher / direct `link_item_*` writes / progression event flags). The location-tracker re-runs `Logic_ComputeReachability` only when the counter advances — not per frame. Per-frame cost is then a static-table read and OAM blit, well within the existing HUD budget. Frame-budget target: tracker overhead < 0.5 ms per frame on reference hardware, < 2 ms on Switch.

### D10. Text-input infrastructure

`main.c` adds an SDL_TEXTINPUT event handler that routes characters into a `RandoTextField` widget when the settings screen is active. The widget is a single-line buffer with cursor, backspace, paste-from-clipboard (Ctrl/Cmd+V via SDL clipboard API), and a fixed character set (the base32 alphabet for share strings, plus a few separators).

On Switch, SDL2's `nx-sdl` does not enable native `swkbd` by default. The Switch build wraps `swkbdCreate`/`swkbdShow` from libnx and routes its result into the same `RandoTextField` buffer. The on-screen alphabet picker is the cross-platform fallback (PC controller, Switch handheld undocked).

Text-input plumbing is a Phase A prerequisite, not a bonus feature. Without it, the settings screen literally can't accept share strings.

### D11. Save-snapshot interaction (rewritten against StateRecorder reality)

The snapshot format is NOT a raw `g_ram` dump. Per [zelda_rtl.c:533](src/zelda_rtl.c:533), `StateRecorder_Save` writes `hdr[8] + log + base_snapshot + SnesState_dump`. The SnesState dump captures `g_ram` (so `kRam_Rando*` cells survive), but the runtime heap state (placement table, settings struct) does not.

**Rando snapshot save path**:
- Before calling `StateRecorder_Save`, the runtime calls `StateRecorder_ClearKeyLog` (force the base_snapshot path) so loaders are guaranteed a SnesState image to restore from. Without this, replay mode falls back to `ZeldaReset(false)` and rando state is gone.
- After `StateRecorder_Save` writes the standard 4 chunks, an optional **tail-TLV chain** is appended for forward-compatibility. Each TLV entry is `magic[8] + type[4] + length[4] + payload`; the loader skips entries with unknown `type`. Phase A defines one type: `TAIL_RANDO_STATE` (payload = generator_version + settings_hash + share_string + placement_table_size + placement_table). Total tail size ≈ 500 bytes. Future features (MSU-1 metadata, replay annotations, etc.) can append additional TLVs without breaking the rando reader.

**Rando snapshot load path** (`StateRecorder_Load`):
- Header read → log read → base_snapshot read → SnesState read; at this point the standard read is complete and the existing `assert(state.p == state.pend)` validates the SnesState. The runtime then attempts to read TLV entries: read 8 magic bytes, then `type[4]` + `length[4]`, then either consume the payload (for known types) or seek past `length` bytes (for unknown types). EOF at any point terminates the loop cleanly. For `TAIL_RANDO_STATE`, the placement table is reinstalled into runtime heap.
- Replay mode (`Ctrl+F1`-`F10`): the base_snapshot is always present for rando snapshots (because of the force above), so `LoadSnesState` is called and `g_ram` is restored before the input log replays — meaning `kRam_RandoSlotActive` is true at frame 0 and every replayed frame's grant-site dispatch fires correctly against the freshly reinstalled placement table.

**Ordering invariant (critical)**: `LoadSnesState` restores `g_ram` including `kRam_RandoSlotActive` *before* the TLV tail is read and the heap placement table reinstalled. **No game frame may execute between these two steps.** If any frame did execute, dispatch would read an empty/stale heap placement table while `kRam_RandoSlotActive` is true, silently corrupting state. The current call site is sequential within `StateRecorder_Load`, so this is satisfied; the spec records this as an invariant so a future refactor doesn't break it accidentally. A code comment in `StateRecorder_Load` at the post-`assert(state.p == state.pend)` exit point documents the invariant and points to design.md §D11.

**Older binaries reading a rando snapshot**: `StateRecorder_Load` stops after `assert(state.p == state.pend)`; the file handle is then closed without reading further bytes. The trailing `RandoSnapshotTail` is discarded harmlessly. Rando state never applies, snapshot loads as vanilla — graceful degradation.

**Newer binaries reading a vanilla snapshot**: the post-SnesState `fread` for magic returns EOF or a non-magic value; rando state simply doesn't load, snapshot resumes as vanilla. No corruption.

### D12. Atomic-commit protocol for sram.dat + sidecar

The existing `ZeldaWriteSram` at [zelda_rtl.c:881-890](src/zelda_rtl.c:881) does `rename("saves/sram.dat", "saves/sram.bak"); fopen(...wb); fwrite; fclose`. This is *almost* the standard write-rename pattern but missing the explicit `fsync` calls — on a crash mid-write, recovery falls back to `sram.bak`. Good enough for vanilla.

For randomizer mode, the rules are:

- **Write sidecar first**, then `sram.dat`. Ordering: any partial write that leaves only sidecar updated (no sram.dat update) is harmless on next load (sidecar marks the slot kind=rando but no fresh vanilla shadow exists; the load sees the existing sram.dat slot which is the pre-write state, and surfaces a "save was interrupted" notice; the player can replay).
- **Each file uses .tmp-then-rename**: `sram_rando.dat.tmp` is written, `fflush` + `fsync` (POSIX) / `_commit` (Win32) called on the file descriptor, then `rename` to `sram_rando.dat`. Same for `sram.dat.tmp`. On POSIX, the containing directory is also fsynced after each rename.
- A `last_vanilla_write_version` field in the sidecar slot header tracks the generator_version under which the *vanilla shadow* was last consistently written. On load, if this field is older than the current binary's version AND the corresponding sram.dat slot has been modified since (detected by SRAM checksum drift recorded in the sidecar), the load surfaces a "this slot was edited by an older build, rando state may be stale" warning and offers two recovery options: continue with embedded placement (default) or convert to vanilla.

This addresses N9's downgrade-then-re-upgrade scenario without adding complex migration code.

### D13. Reachability-state counter (renamed from inventory_change_counter)

The earlier draft called this `inventory_change_counter` and bumped only on inventory writes. That misses a critical class of reachability triggers: **non-inventory state transitions** that flip predicate results. Examples:

- Aga 1 defeated → Pyramid opens → Pyramid Fairy reachable (no inventory change)
- Boss death flag set → `OP_DUNGEON_CLEARED <dungeon>` flips → boss reward becomes reachable for tracker purposes
- Mushroom turned in at witch's hut → magic powder available (event flag, no item-byte change in the dispatched item view at that moment)
- King's Tomb item taken → boots-dash precondition satisfied
- Sahasrahla satisfied (Pendant of Courage delivered) → Sahasrahla gift available

Without bumping on these, the location-tracker silently shows stale "unreachable" cells until the next item pickup unrelated to the actual progression.

**Renamed to `reachability_state_counter`**. Bumps in three places:

1. Inside `Rando_OnLocationCheck` whenever a substitute is granted.
2. Inside audit-exempt direct `link_item_*` write sites (build-time audit guard enumerates these).
3. Inside any documented **progression event flag** write site enumerated in `audit.md` §"Reachability-affecting events". Examples Phase 0 must record: Aga 1 defeat flag, dungeon-boss-cleared flags, NPC-satisfied flags (sahasrahla, sick kid, mushroom→powder), special event flags (master sword pulled, pyramid opened, etc.).

The audit deliverable adds a section "Reachability-affecting events" enumerating every event flag the logic graph references, with file/line for the existing write site. The bump call is one line per site; trivial cost.

The inventory address range trackers observe is pinned in Phase 0 (task 0.7) as `g_ram[0xF340..g_ram_inventory_end]`; the exact end offset is recorded in `audit.md`.

### D14. Phase A sub-phasing

### D15. CLI / headless generation mode

Two invocation forms:

- Single seed: `./zelda3 --generate-seed --settings=<key=value,...> --seed=<u64> --out-spoiler=<path> [--out-share-string=<path>] [--budget-seconds=<n>]`
- Batch from manifest: `./zelda3 --generate-seed --manifest=<yaml> [--budget-seconds=<n>] [--out-dir=<path>]`

The manifest YAML lists N (settings, seed_u64) pairs; the binary generates all N seeds in a single process invocation, writing one spoiler per pair to `<out-dir>/<share_string>.json`. The regression-corpus CI job uses this form: 50 seeds × per-platform iteration is one binary launch per platform, not 50.

Both forms exit after writing spoilers without opening the SDL window or running the game. Use cases:

- The regression-corpus CI job iterates over 50 (settings, seed) pairs; UI-only generation would require window/swkbd plumbing in headless CI.
- Race admins generating bulk seeds.
- External tournament tooling that wants to bulk-validate share strings against current logic.
- Automated bisection of generator regressions.

CLI mode bypasses the asset-hash warn dialog (CI typically runs against vanilla assets); a `--assets-must-be-vanilla` flag refuses if the loaded blob differs from `kVanillaAssetsHash` and exits non-zero.

The `--budget-seconds` option overrides the 5-second default for pathological settings combinations; the CLI emits the actual wall-clock used to stderr.

### D16. 5-icon visual hash for at-a-glance seed verification

ALTTPR convention is a deterministic 5-icon strip drawn from a curated atlas of inventory icons (bow, boomerang, hookshot, mushroom, etc. — the exact list is curated at A2 implementation time when `icon_atlas.yaml` is authored; the inline examples in this section are illustrative, not normative) shown on the file-select banner and in the in-game pause menu. Racers use it for "are we on the same seed" verification at the start of a tournament — without it, the only way to confirm seed identity is comparing share strings, which is awkward on a TV with no text overlay.

**Input — critical**: the icon hash MUST be derived from the **full seed identity**, not from `settings_hash` alone. `settings_hash` is constant across every seed sharing the same settings; deriving icons from it would have two racers on different seeds see identical icons. Two valid inputs:

- `SHA-256(share_string_binary)[0..5]` — full seed identity (settings + seed_u64 + magic + checksum)
- `SHA-256(settings_hash || seed_u64)[0..5]` — equivalent in entropy

Phase A uses the first (`SHA-256(share_string_binary)[0..5]`).

**Atlas size**: ALTTPR's icon atlas is larger than 32 (no exact match to a power of two). The implementation pins `N = |kHashIconAtlas|` from the canonical icon list authored in `assets/rando/icon_atlas.yaml`. Each of the 5 icon indices is `SHA-256(share_string_binary)[i] mod N`; do not assume `N == 32`. The atlas YAML records the icon set and orders it; bumping the atlas (adding/removing entries) advances `generator_version` because it changes the icon-hash output for every existing share string.

**Modulo bias**: the `mod N` mapping introduces statistical bias toward low indices by up to `1/N` (worst case when `N` is just above a power of two). Acknowledged and tolerated; the icon hash is **not cryptographic** — its purpose is at-a-glance verification, not security. Rejection sampling to remove bias would be overkill.

Rendered as a row of 5 OAM tiles on the file-select rando banner and on the pause-menu HUD. Cheap; one new OAM block.

### D17. QoL features policy

The user's existing `kFeatures0_*` settings (fast text, palette tweaks, dim flashes, etc.) are **not** changed by starting a rando slot. The settings screen surfaces a "Recommended for randomizer" panel with toggles for the QoL features ALTTPR ROMs typically enable by default (e.g., fast text, skip intro on keypress, max items in yellow), with each toggle initialized to the user's current value and an "Apply recommendations" button that flips them all to recommended. The user opts in explicitly.

Without this policy, the first ticket will be "my rando seed shipped without fast text and I had to mash through 200 chests." The opt-in tray makes the trade-off visible at slot creation.

## Risks / Trade-offs

- **Logic-graph translation is the long pole of Phase A1**: hand-translating ALTTPR's PHP closure logic into YAML/bytecode. **Concrete scope** (verified by reading the source): `alttp_vt_randomizer/app/Region/{Standard,Open,Inverted}/*.php` is ~4,000 lines of PHP wiring per-location `setRequirements` closures, plus `setFillRules` / `setAlwaysAllow` for placement, plus per-region `can_enter` / `can_complete`. The 43 named macros on `app/Support/ItemCollection.php` (`canShootArrows`, `canKillMostThings`, `canGetGoodBee`, `hasBottle`, `canExtendMagic`, `canBlockLasers`, etc.) become our macro set directly. → Treated as A1's risk-dominant task. ALTTPR is MIT-licensed (verified against its `LICENSE` and `composer.json`); hand-translation is an MIT-derivative work, fully compatible with this repo's MIT license, requiring only upstream attribution. Mitigations: (a) macros from day 1, copying ALTTPR's factoring rather than inventing one; (b) audit table pairing each YAML predicate with its ALTTPR source-file:line — doubles as documentation and as the upstream-drift detector; (c) explicitly name a human who owns logic translation and the regression corpus together; (d) **bus-risk mitigation**: translation work is committed in reviewable chunks (≤ 30 locations per PR) with the regression corpus growing alongside each chunk; a second reviewer with ALTTPR domain familiarity is named as backup. A0.5 (vertical-slice demo with hardcoded C logic for ~20 sites) derisks the integration surface so A1's pole isn't blocked by integration bugs.

- **Logic-graph maintenance** going forward: ALTTPR's logic evolves. → Pin to a specific upstream commit for *content reference* only, advance our own regression corpus when we bump. Generator version increments lock seeds to the logic they were generated against; embedded placement (D6) removes the upgrade-breaks-saves failure mode.

- **Placement-override completeness**: missing a grant site means the player gets the wrong item silently. → Phase 0 audit deliverable lists every site explicitly before any implementation begins. Audit comment convention; build-time check that new writes outside dispatch include an exemption comment.

- **Phase-A logic scope is restrictive**: `tricks=none` and `logic=NoGlitches` rule out a meaningful chunk of advanced-rando settings (boots-clip, fake-flipper, dark-room nav, OWG, MG, etc.). Note: `item_pool_difficulty` is *fully* supported in Phase A (easy/normal/hard/expert), as it affects only pool composition not predicate logic. → Documented as Phase A scope. The VM op set is forward-compatible: Phase B's trick and glitch-level ops slot in without restructuring.

- **Save format proliferation**: introducing a sidecar file means two save files to keep coherent (`sram.dat` + `sram_rando.dat`). → Stale sidecar (no matching `sram.dat` slot) is harmless and surfaces as the "recovered" badge per `randomizer-save / Orphan sidecar handling`. Missing sidecar (vanilla install) is the normal vanilla path. Atomicity is per §D12: write-temp + fsync/_commit + rename + directory-fsync, sidecar before `sram.dat`. An earlier draft used a "final commit byte" approach which was insufficient on modern filesystems; the write-temp-then-rename pattern is sound and matches the existing `ZeldaWriteSram` convention. Cross-file drift after a crash between sidecar and `sram.dat` writes is detected by `sram_slot_checksum_at_last_write` (per `randomizer-save / Downgrade-then-re-upgrade safety`).

- **RAM-cell additions risk vanilla divergence**: see D7. → Init-order rule + vanilla-replay CI test catches this.

- **Text-input on Switch**: libnx `swkbd` integration is a new dependency on a libnx API. → Phase A item; budget is modest (well under a day's work) but should not be elided.

- **Generation performance**: pathological settings could push generation past a second on Switch. → Forward-fill fallback after 5-second budget; **report wall-clock and the `forward_fill_fallback` warning prominently in the spoiler header** so racers don't unknowingly play a degenerate-quality seed. CLI mode (`--budget-seconds`) allows raising the budget for complex configurations (keysanity + retro + restrictive item-pool); 5 seconds is the default and is too low for some setting combinations. The settings screen surfaces an estimated-budget warning when toggling shuffles known to inflate generation time.

- **RAM-compare incompatibility**: by design, randomizer mode disables RAM-compare. → Vanilla play is unaffected.

- **No multiworld foothold**: by deliberately not pre-architecting for a push API, a future multiworld change will need to add the push path itself, not just hook into a pre-existing one. → Acknowledged trade-off; pre-architecting for hypothetical multiworld would bloat Phase A.

## Migration Plan

- **No data migration required.** Existing vanilla `saves/sram.dat` files load unchanged.
- **Rollback path**: if a user downgrades binaries, `sram_rando.dat` is simply ignored by older builds. Vanilla `sram.dat` still loads. No file is corrupted; the rando slot's vanilla shadow in `sram.dat` represents the player's basic progress (HUD displays whatever items the rando dispatcher granted, persisted as ordinary `link_item_*` writes).
- **Phased rollout**:
  - Phase A (v1.0): item + dungeon-item shuffle (per-class modes), prize shuffle, medallion shuffle, world-state modes, 7 goals (`ganon`, `fast_ganon`, `dungeons`, `pedestal`, `triforce-hunt`, `ganonhunt`, `completionist`), `tricks=none` + `item_pool∈{easy,normal,hard,expert}` + `logic=NoGlitches`, spoiler log, share string, sidecar save (kind-toggle), text-input infrastructure, settings screen, 5-icon hash, CLI mode.
  - Phase B (v1.1): trick predicates, glitch-logic-level predicates, **hint generation system** (Sahasrahla telepathic tiles, storyteller, bookshelves, Murahdahla for Triforce Hunt — per ALTTPR's `app/Services/HintService.php`; casual players consider hints integral to the experience and Triforce Hunt is almost unplayable without them), race-mode spoiler suppression with reveal, in-game item & location trackers, boss shuffle, drop-pool shuffle, `swordless` weapon mode, `pyramid_bow_upgrade=arrows`, `accessibility=none`.
  - Phase C (v1.2): entrance shuffle (Simple, Restricted, Crossed, Insanity).
  - Phase D (v2.0+): cosmetic shuffles, major-glitch logic, EmoTracker auto-tracker server.
  - Multiworld: deferred to a separate OpenSpec change that adds the push API and networking.

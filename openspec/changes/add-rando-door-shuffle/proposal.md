## Why

Door shuffle is the most ambitious randomizer axis on the roadmap: it randomizes the **internal door-to-door connections inside dungeons**, not just which overworld door reaches which dungeon (that is the already-shipped entrance shuffle). After a door shuffle, Eastern Palace's lobby might open onto Swamp's flooded hub; a small-key door that vanilla puts three rooms deep might gate the first room. It is the headline feature of the upstream **ALttPDoorRandomizer** project (`C:\src\ALttPDoorRandomizer`, the reference for this change).

This change exists because door shuffle is *architecturally novel for this fork*, and the plan must be gotten right before code lands. Four research findings frame everything:

1. **The runtime engine has NO normal-door destination table.** Unlike the SNES ROM (which ALttPDoorRandomizer patches), the zelda3 C reimplementation computes a normal edge-door's destination *positionally* — walking off the east edge of room `R` loads `R+1`, north loads `R-0x10` (`Dungeon_StartInterRoomTrans_Right/Left/Up/Down`, `src/dungeon.c:8188, 2059, 2099, 2142`). There is nothing to "patch." Redirecting a door means **adding an indirection layer** at those four functions (plus the staircase/hole/teleport-door sites). The good news: the engine *already* has the exact primitive needed — the vanilla **teleport-door** path reads an arbitrary destination room from the room header and calls `Dungeon_AdjustForTeleportDoors` (`src/dungeon.c:8149`) to reposition Link + camera into any room. Door shuffle generalizes that one mechanism to every shuffled door.

2. **The staircase/hole/teleport subset IS already table-driven.** Those transitions read `dung_hdr_travel_destinations[0..4]` (room-header bytes 9–13). They can be redirected by overriding five bytes per room — far easier than the positional normal-door case.

3. **The logic engine cannot express intra-dungeon connectivity today.** Reachability is a *region graph where an entire dungeon is one node* and small keys are modeled as inventory *count thresholds* baked for the vanilla layout (`HAS_AMOUNT(SmallKey_PalaceOfDarkness, 5)` etc. in `assets/rando/logic_parts/*.yaml`). A shuffled door layout changes which locations sit behind how many keys and whether they are reachable at all — none of which is expressible in the shipped graph. Door shuffle needs a **new per-seed dungeon-interior solver** feeding the placer.

4. **The reference is ~550 KB of Python** (`DoorShuffle.py` 247 KB + `DungeonGenerator.py` 198 KB + `KeyDoorShuffle.py` 108 KB). The hardest parts — the cross-dungeon polarity/sector-distribution engine and the exponential key-door softlock prover — must be reimplemented in C. We do **not** need seed-parity with ALttPDoorRandomizer (we define our own door-layout format + RNG salt), which frees the port from replicating Python dict-iteration order.

Because the runtime risk and the generation risk are independent and both large, this change is **staged so each milestone is independently shippable and playtestable**, and the committed scope is the de-risking foundation plus a playable basic MVP. The full design (all intensities, crossed dungeons, door-type/trap/decouple shuffle) is captured in `design.md` and split into explicit follow-on changes.

## What Changes (committed scope = Milestones A + B)

**Milestone A — Foundations & identity (de-risk the runtime layer with zero behavior change):**
- Codegen the **static door/room topology** from the reference (`assets/scripts/gen_door_tables.py`, mirroring the in-tree `gen_entrance_table.py` / `gen_inverted_maps.py` codegen pattern) into gitignored C tables: a canonical door-stub catalog (stable id ← `(room, edge, slot, layer)`), each stub's type/kind/default partner, per-room environment (header bytes, dungeon id), and the vanilla door-type counts.
- A runtime **sparse door-redirect layer** (`src/rando/door_runtime.{c,h}` new): a per-seed table `Rando_DoorRedirect(room, edge, slot, vanilla_dest) → dest_room | NO_OVERRIDE`, consulted at the four `Dungeon_StartInterRoomTrans_*` functions and the staircase/hole/teleport-door sites, all behind a new `kFeatures1_DoorShuffleActive` bit. **Identity table = every entry `NO_OVERRIDE` ⇒ byte-for-byte vanilla behavior** (RAM-compare clean, corpus untouched). This proves the redirection plumbing before any shuffle exists.
- The generalized **arbitrary-room arrival** routine (extend `Dungeon_AdjustForTeleportDoors` to take an arrival edge/slot, not just a room) + camera/quadrant/plane/floor coherence.

**Milestone B — Basic door shuffle MVP (playable, beatable, softlock-free):**
- A new **door-shuffle generator** (`src/rando/shuffle_doors.{c,h}` new): `doorShuffle = basic` (within a single dungeon), `intensity = 1` (normal + spiral-stair doors only), `door_type_mode = original` (vanilla key/door counts), small keys restricted **in-dungeon**. Ported from the reference: the sector builder (`convert_to_sectors`), the stitcher (`DungeonStitcher`'s random-proposal + local-repair with crystal-barrier-aware `ExplorationState` reachability), and the **key-door softlock prover** (`KeyDoorShuffle.analyze_dungeon`/`validate_key_layout`). Single-dungeon only ⇒ the trivial `simple_dungeon_builder` path, **skipping the hardest component (the polarity engine).**
- **Logic half**: a per-seed **dungeon door-graph** over codegen'd per-room regions (the reference's room-granular `dungeon_regions`), wired each seed via the entrance-shuffle-proven per-seed primitives (region reassignment + added-edges-with-predicate-offset, sized up for the door graph), with per-door small-key thresholds expressed by selecting a **precompiled** `HAS_AMOUNT(SmallKey_X, k)` predicate (worst-case N, which is safe) and `bk_restricted` honored as a big-key placement ban. NOTE: the pre-review plan to inject *arbitrary* per-seed predicates through the existing override seam was found **infeasible** (that seam carries static-stream offsets only) — see `design.md §4`. The room regions are inert when door shuffle is off ⇒ vanilla reachability byte-identical.
- **Settings / save / UI / version / corpus** plumbing for the new axes, following the enemy-shuffle checklist.

## Capabilities

### New Capabilities

- **`randomizer-door-runtime`** — the in-game door-transition redirection engine: the per-seed door-link table, the four transition-site hooks, the generalized arbitrary-room arrival (Link position + camera + quadrant + plane/floor), and the environment/shutter coherence rules. Peer to `randomizer-inverted-runtime`.

### Modified Capabilities

- **`randomizer-shuffles`** — ADDED Requirement "Door shuffle generation": the `doorShuffle`/`intensity`/`door_type_mode` axes (committed scope: `basic` + intensity 1 + `original`), the stitcher, the key-door softlock prover, and the door-type assignment, with a beatability + no-softlock contract.
- **`randomizer-logic`** — ADDED Requirement "Per-seed dungeon door-graph": door shuffle feeds reachability via a per-seed door-edge graph over codegen'd per-room regions (inert when off), with precompiled per-door small-key-threshold predicates; `doorShuffle == vanilla` ⇒ byte-identical reachability (corpus invariant preserved).
- **`randomizer-placement`** — ADDED Requirement: assumed-fill consumes the per-seed key-door predicates; in-dungeon small-key containment stays consistent with the door layout.
- **`randomizer-core`** — ADDED Requirement: the door-shuffle axes in canonical serialization (committed scope packs into the free pad byte `[27]`; the full feature's wider axes are flagged as requiring the `kSettingsCanonicalLen` cascade). Authored as ADDED, not MODIFIED, because the baseline "Settings canonical serialization order" requirement is stale relative to the as-built `[25]/[26]` axes — see `design.md §5`.
- **`randomizer-save`** — ADDED Requirement: the door layout is **regenerated from `(seed, settings, door_attempt)` at load, not serialized**; a `door_attempt` byte joins the reserved sidecar tail. Version drift is **blocking** for door-shuffle slots (a drifted layout can make the serialized placement unbeatable — unlike entrance shuffle's non-blocking warning), or a persisted layout digest hard-fails activation.

## Impact

- **Code (new):** `src/rando/door_runtime.{c,h}`, `src/rando/shuffle_doors.{c,h}`, `src/rando/door_keylogic.{c,h}` (the key-door prover), `assets/scripts/gen_door_tables.py`, `assets/rando/door_registry.yaml` (stable door-stub ids). **Code (touched):** `src/dungeon.c` (≈6 transition-site hooks + generalized arrival), `src/rando/rando_settings.{c,h}`, `src/rando/rando_save.{c,h}`, `src/rando/rando_generate.c`, `src/rando/rando.c` (slot-load regen + runtime install/teardown), `src/rando/rando_logic.c` (per-seed door-graph + per-room regions + reachability-cap bump), `src/rando/rando_placement.c`, `src/features.h` (new flag + runtime RAM), `src/rando/rando_window/*` (UI), `assets/scripts/{bump,run}_rando_corpus.py`.
- **Assets:** gitignored codegen output (`src/rando/door_tables.gen.h` or equivalent) — fails-open like `chest_table.gen.bin`, so the build guard + a self-test must catch an empty table (see `design.md §10`).
- **Effort / bottleneck:** Large — comparable to the original randomizer-support change. The real bottleneck is **not** token volume but the **playtest loop**: the slot path has no automated net (corpus + `--rando-selftest` cover only generation, never the runtime door redirect or the key prover's end-to-end correctness), so every milestone is gated on hand-playtesting redirected dungeons. Milestone A's identity test is the one piece with an automatable check (corpus byte-identical).
- **Regression risk:** `kGeneratorVersion` bumps; corpus regenerates. `doorShuffle == vanilla` MUST stay byte-identical (Milestone A enforces it before any shuffle exists).
- **Out of scope (follow-on changes, designed but not built here):** intensity 2/3 (open-edges, straight-stairs, ladders, lobby/portal shuffle — couples with entrance shuffle); `door_type_mode` big/all/chaos + trap-door shuffle/removal; decouple (one-way) doors; **crossed/partitioned** modes (the polarity/sector-distribution engine + cross-dungeon environment porting — the single hardest runtime+gen surface); wild/universal key modes × door shuffle; pottery/key-drop pools.
- **ALTTPR provenance:** door rando is a **separate codebase** from the ALTTPR PHP this fork otherwise mirrors — none of the placement/logic PHP applies. The reference is `C:\src\ALttPDoorRandomizer` (MIT, verify `LICENSE`). Claim-grounding discipline applies: read the actual Python, not memory.

## Status

**Scoped 2026-06-09** via four parallel research agents over the reference + the C runtime + the fork's rando infrastructure. `design.md` captures the architecture (the two-halves model scaled up, the sparse-override runtime, the per-seed key-door solver, the staged milestones, and every cross-dungeon hazard inherited from boss shuffle's "environment isn't carried by a sprite redirect" lesson). The plan is intentionally **functional-first**: Milestone A ships an identity redirect with an automatable correctness check before any randomness is introduced.

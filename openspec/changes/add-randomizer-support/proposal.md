## Why

The community A Link to the Past randomizer (ALTTPR) is the dominant way modern players engage with this game, but the only path to play it today is the original ROM patched with a community seed — meaning emulators, IPS/BPS handling, and zero of the port's quality-of-life improvements (widescreen, MSU-1, save snapshots, frame-perfect rewind, modern input). This port already reimplements the full game in C and recently added BPS patch support (commit `fbbb3f9`), so the foundation exists to make this repo the best place to play randomized seeds. A built-in seed generator removes the external website dependency entirely and lets the port own the player experience end-to-end: generate, play, track, and route — all in one binary.

## What Changes

- Add a native ALTTPR-informed seed generator: item shuffle with logic, dungeon-item shuffle modes, optional entrance and boss shuffles, world-state modes (Open / Standard / Inverted / Retro), goals (Defeat Ganon / Fast Ganon / All Dungeons / Pedestal / Triforce Hunt), and item-pool difficulty.
- Add a randomizer settings screen reachable from the file-select flow. Each of the existing three save slots gains a *kind* (vanilla or randomizer) tracked in the sidecar file; the file-select screen shows each slot with the appropriate banner. Starting a new game on an empty slot prompts the player to choose kind, and selecting randomizer opens the settings screen. **No 4th file-select entry is added** — the 8 KB `sram.dat` has no room (it is 3 slots × {primary, backup} = 7.5 KB consumed; see design.md §D8 for the analysis).
- Add a placement layer that overrides vanilla item-grant sites by location ID via a single dispatch function. The dispatcher takes both `(location_id, vanilla_item_id)` so unknown IDs can safely fall back to the vanilla grant.
- Add a logic engine (region/location graph + item-requirement predicates compiled from YAML) that backs both seed generation and an optional in-game tracker overlay.
- Add a spoiler log writer (text + machine-readable JSON) and a share-string format unique to this port.
- Add randomizer-only HUD elements: settings banner on file select with a **5-icon visual hash** (deterministic icon-pick from `settings_hash` — bow/boomerang/hookshot/etc. as 8×8 tiles per ALTTPR convention, used by racers for at-a-glance seed verification), the same 5-icon hash shown in the in-game pause menu, optional item & location trackers.
- Add a **CLI / headless generation mode**: `./zelda3 --generate-seed --settings=<key=value,...> --seed=<u64> --out-spoiler=<path>` for a single seed, plus `./zelda3 --generate-seed --manifest=<yaml>` for batch generation from a YAML manifest listing N (settings, seed_u64) pairs → N spoilers in a single process invocation. Needed for race admins, batch corpus regeneration, automated tournament tooling, and the regression-corpus CI job itself (one binary launch instead of 50).
- Extend save storage with a sidecar file (`saves/sram_rando.dat`) that mirrors the slot layout of the existing `saves/sram.dat` and stores per-slot randomizer state. The existing `sram.dat` format is **unchanged** and vanilla-only readers remain fully compatible.
- Add an SDL2 text-input layer (basic single-line text field + on-screen alphabet picker) for share-string entry across PC and Switch builds. The vanilla game has no text-input infrastructure today.
- Gate every divergence from vanilla behavior behind a new feature flag bank (`kFeatures1_*`) stored alongside `kFeatures0_*` so RAM-compare verification mode is unaffected when no randomizer slot is active.

### Phase A is internally split into A0 / A0.5 / A1 / A2

Phase A as originally framed (full item-shuffle ship-it) is several months of work. To reduce integration risk and surface UX/architectural problems before the months-long logic-translation effort starts, Phase A is internally subdivided. Each sub-phase has independent acceptance criteria in tasks.md §14.

- **Phase A0** — Foundation: Phase 0 audit, RNG, share string, SHA-256, feature flag plumbing, asset-hash warn-flow, `Rando_OnLocationCheck` dispatcher skeleton (one wired grant site), no UI. Dev-only flag flips rando mode.
- **Phase A0.5** — **Vertical-slice playable demo**: one world state (Open), one goal (Fast Ganon), ~20 hand-curated grant sites, hardcoded C-side logic (no YAML codegen yet), real placement, real sidecar save/load, file-select kind-toggle, snapshot tail. The point isn't to ship — it's to flush out integration issues (file-select rendering, snapshot tail dispatch ordering, asset-hash UX, save round-trip, dispatcher fall-back) before committing to translating 200+ ALTTPR predicates into YAML. If the kind-toggle or snapshot tail design has a fundamental issue, A0.5 catches it after ~2 weeks of work, not 12. Acceptance: a playable seed end-to-end from settings → boss kill, with all save/load/snapshot/tracker paths exercised at least once.
- **Phase A1** — Logic + placement: full `logic.yaml` (200+ predicates × 4 world-states — the long pole; budget realistically), item registry with all progressive/bottle/junk types, location registry, predicate VM with named macros (`CanKillMostThings`, `CanDamageBoss`, `CanGetGoodBee`, `CanShootArrows`, etc.), reachability with per-iteration memoization, goal predicates (all 7 Phase A goals including Ganon Hunt and Completionist), item pool + assumed fill + forward-fill fallback, prize shuffle, medallion shuffle, spoiler writer (ALTTPR-mirrored JSON schema), regression corpus, CLI generation mode.
- **Phase A2** — Save + UI + integration: sidecar atomic-commit, file-select kind-toggle (visual 5-icon hash banner per ALTTPR convention), settings screen, text-input infrastructure, snapshot tail-TLV, all remaining grant sites per audit, in-game pause-menu hash display.

A1 is the riskiest sub-phase; A0.5 derisks it by validating the integration surface before A1's months-long logic translation begins.

### Phase A scope (this change) and out-of-scope reductions

To make Phase A buildable, the following are explicitly scoped to Phase A and listed here so reviewers can flag if anything should be promoted:

- **Phase A logic axes** — three independent ALTTPR settings, each pinned individually:
  - **Trick logic (`tricks`)**: pinned to `none`. Individual trick predicates (boots-clip, fake-flipper, bunny-revival, dark-room nav, bomb-jump, etc.) are reserved as `OP_TRICK` placeholders in the op registry but inactive in Phase A.
  - **Item-pool difficulty (`item_pool_difficulty`)**: Phase A supports `easy`, `normal` (default), `hard`, `expert`. This is **independent** of trick logic and glitch logic — pool construction handles all four difficulties via the existing pool-building step; the placement algorithm is unchanged. `Rupoor` only enters the pool at `hard`/`expert`. Including this axis costs little and is a meaningful Phase A player-experience win.
  - **Glitch logic (`logic`)**: pinned to `NoGlitches`. `OverworldGlitches`, `MajorGlitches`, `HybridMG`, `NoLogic` are reserved as `OP_GLITCH_LEVEL_AT_LEAST` placeholders and ship in a later phase.
- **Goals**: Defeat Ganon, Fast Ganon, All Dungeons, Pedestal, Triforce Hunt (pedestal-end), **Ganon Hunt** (Triforce Hunt where the final action is killing Ganon; distinct from pedestal-end Triforce Hunt — per `Randomizer.php:108-110`), **Completionist** (every location must be reachable; forces `accessibility = locations`). Triforce Hunt and Ganon Hunt support independent `pieces_required` and `pieces_placed` settings. Fast Ganon and Ganon Hunt expose **two independent crystal-count settings**: `crystals.ganon` (how many crystals make Ganon vulnerable) and `crystals.tower` (how many open Ganon's Tower) — these are routing-relevant and must be settable separately.
- **World-states**: Open, Standard, Inverted, Retro.
- **Shuffles in Phase A**: item shuffle; dungeon-item shuffle modes (see below); **prize shuffle** (which dungeon yields each crystal / pendant — has logic interactions: Green Pendant gates Sahasrahla, all 7 crystals gate Ganon, the three colored pendants gate the Sword Pedestal); **medallion shuffle** (which of Bombos/Ether/Quake opens Misery Mire and Turtle Rock entrances — even default ALTTPR randomizes this).
- **Shuffles deferred** to later phases: boss shuffle (which boss occupies which boss room — separate from prize shuffle), entrance shuffle, drop-pool shuffle, cosmetic shuffles.
- **Dungeon-item modes** — separate setting per item class (small keys, big keys, maps, compasses), each with three modes: `Vanilla` (original location), `Dungeon` (anywhere in source dungeon — equivalent to ALTTPR's `wildKeys=false`), `Wild` (anywhere in the world pool — equivalent to ALTTPR's keysanity). These affect `|pool|` and `|locations|` cardinality and therefore junk-padding.
- **Boss-heart-in-pool / boss-hearts-as-items**: deferred to Phase B (per `Randomizer.php:155-169`'s `region.bossHeartsInPool` and `region.bossesHaveItem`). Phase A pins the 10 boss-heart slots (`<Dungeon>_BossHeart`) to **identity placement**: the dispatch still fires (uniform code path), but the placement table entry for each of those slots is hardcoded to `BossHeartContainer`. The boss-heart locations are NOT part of the placement permutation; their items are NOT in the shuffled item pool; `bossHeartsInPool` does not appear in the canonical-serialization order because there is nothing to toggle in Phase A. Phase B adds the setting and lets these slots participate in the shuffle.

- **Setting axes pinned for Phase A** (each requires a final value to avoid setting-struct surgery later):
  - **`mode.weapons`** (per `Randomizer.php:224`): supported Phase A values are `randomized` (default) and `assured` (Link starts with one guaranteed sword in the pool). `vanilla` and `swordless` are reserved for Phase B — `swordless` in particular changes "can damage Ganon" predicate semantics (silvers + something to start) per `Randomizer.php:230-240` and is non-trivial.
  - **`accessibility`**: Phase A supports `items` (default — every progression item is reachable) and `locations` (every location reachable; auto-set when goal is Completionist). `none` (no accessibility guarantee, allows unreachable junk) deferred to Phase B.
  - **`pyramid_bow_upgrade`** (per `Randomizer.php:150-152`): pinned to `silvers` (Pyramid Fairy grants Bow+Silvers); `arrows` variant deferred to Phase B. This is logic-affecting because silvers gate Ganon.

  These are the *settings-struct* axes; their canonical serialization order is part of `settings_hash` and is documented in `audit.md` §"Settings serialization order".
- **Items**: placements are restricted to item IDs in the registry. The Phase A registry includes:
  - **Progressive items** (foundational to ALTTPR placement semantics — see `Randomizer.php:183-198`): `ProgressiveSword` (L1→L2→L3→L4), `ProgressiveShield` (Fighter→Red→Mirror), `ProgressiveArmor` (Green→Blue→Red), `ProgressiveGlove` (Power→Titan), `ProgressiveBow` (Bow→Bow+Silvers). Distinct IDs from absolute counterparts (`L1Sword`, `FighterShield`, etc.).
  - **Absolute items**: all vanilla `link_item_*` items individually addressable. Includes `SilverArrowUpgrade` as a **standalone item** for non-progressive bow mode (when `mode.weapons` selects absolute, silvers are a separate upgrade item per `Randomizer.php:178-179`).
  - **Bottle-with-contents** as distinct item IDs: `BottleEmpty`, `BottleWithFairy`, `BottleWithBee`, `BottleWithGoodBee`, `BottleWithRedPotion`, `BottleWithGreenPotion`, `BottleWithBluePotion`. Predicates use `HAS_ANY_OF Bottle*` for "has any bottle" and `HAS_ANY_COUNT Bottle* 2` for "has ≥ 2 bottles".
  - **Magic upgrades** (often missed): `HalfMagic`, `QuarterMagic` — modify `link_magic_consumption`, not a `link_item_*` byte; granted by witch's hut and shuffleable as items.
  - **Triforce piece** — `TriforcePiece`. **Required by both Triforce Hunt and Ganon Hunt goals**; pool-padded based on `pieces_placed`. Earlier drafts omitted it, which would have made both goals unimplementable.
  - **Heart-related items as distinct IDs**: `PieceOfHeart` (4 = 1 heart container of effect, the standard PoH from overworld) and `BossHeartContainer` (full container drop from boss kills, +1 max HP directly without the 4-quarters mechanic). ALTTPR keeps these separate; the dispatcher routes accordingly.
  - Small keys, big keys, maps, compasses (per dungeon).
  - Multi-tier rupees: `Rupee1`, `Rupee5`, `Rupee20`, `Rupee100`, `Rupee300`.
  - **Junk-pool**: `SmallMagic`, `Arrow1`, `Arrow10`, `Bombs1`, `Bombs3`, `Bombs10`. `Rupoor` is **available** in Phase A but **only enters the pool when `item_pool_difficulty ∈ {hard, expert}`** (see Phase A axes below).
  - The Phase 0 audit cross-references each ID to its grant-site dispatch path. The well-formedness pass asserts every `OP_HAS_ITEM <id>` predicate and every goal predicate references an item in the registry.

### Explicit non-interactions

- **MSU-1**: orthogonal. Randomizer mode runs with whatever MSU-1 configuration the user has set. No cross-feature behavior change.
- **Non-vanilla asset data**: warn-and-let-the-player-decide, not hard-block. Most players who use this port have sprite packs, palette mods, MSU-1 packs, or community translations — refusing rando-mode for *any* asset deviation would lock out most of the audience. Phase A computes SHA-256 of the loaded asset blob and compares to a vanilla baseline (`kVanillaAssetsHash`, generated by `restool.py`). On mismatch, the settings screen surfaces a per-hash dialog the first time the player tries to generate a seed with that asset blob: "Your asset data differs from vanilla. If your modifications change chest contents or NPC item tables, placement may misbehave; cosmetic changes (palettes, sprites, music) are safe. [Always allow / Allow once / Cancel]". Choice persists keyed by `(asset_hash, decision)` in `zelda3.ini`. Phase B refines this to a **subset hash** computed only over the asset blobs the placement layer depends on (chest tables, NPC gift IDs), so cosmetic mods don't even trip the warning.
- **Save snapshots** (`Shift+F1`-`F10`): the existing `StateRecorder` system saves an input log + a `SaveSnesState` dump (see [zelda_rtl.c:533-558](src/zelda_rtl.c:533)), not a raw `g_ram` dump. Rando snapshots force the `base_snapshot` path (call `StateRecorder_ClearKeyLog` immediately before save) so the SnesState fully captures `g_ram` including the `kRam_Rando*` cells, and append a `RandoSnapshotTail` block containing the placement table after the existing on-disk format. Older binaries reading the snapshot consume exactly the documented number of bytes for the SnesState dump and stop, ignoring the tail; the rando state simply doesn't apply, which is graceful degradation. Replay mode (`Ctrl+F1`-`F10`) requires the base snapshot to be present (rando snapshots always satisfy this), so replay restarts from the snapshotted frame with full rando state.
- **RAM compare side-by-side mode**: incompatible with randomizer slots by design. When a randomizer slot is active, RAM-compare against an attached original ROM is auto-disabled. Vanilla slots are unaffected.

## Capabilities

### New Capabilities

- `randomizer-core`: The seed-generation pipeline — RNG seeding from share string, item pool construction (including junk padding), logic-driven placement (assumed/forward fill), settings application, spoiler-log emission, and share-string format.
- `randomizer-logic`: The logic graph — locations (identified by stable numeric IDs from a registry file), regions, entrances, requirement predicates (bytecode VM with explicit op set covering items, item amounts, world-state, goals, dungeon flags, and a region-reachability primitive), reachability search with a measurable time budget, and goal-completion predicates.
- `randomizer-placement`: Runtime override layer that intercepts vanilla item-grant sites by location ID. Single dispatch function `Rando_OnLocationCheck(location_id, vanilla_item_id)` per grant site. No multiworld push API in Phase A; multiworld is out of scope and not pre-architected here.
- `randomizer-shuffles`: Independent shuffle modules — entrance shuffle (Simple / Restricted / Crossed / Insanity), boss shuffle, drop-pool shuffle, cosmetic shuffles. Each toggleable independently. Phase A defers all of these to later phases; the spec is written here to set the contract.
- `randomizer-ui`: SDL2 text-input infrastructure, file-select re-layout to accommodate a randomizer entry, settings screen, on-screen alphabet picker, optional in-game item & location trackers.
- `randomizer-save`: Sidecar save file (`saves/sram_rando.dat`) parallel to `sram.dat`, per-slot rando metadata block (generator version, settings hash, share string, full embedded placement table, checked-location bitmap), upgrade-pinning rules, race-mode spoiler suppression.

## Phase 0 audit (required prerequisite)

Before any implementation tasks: a deliverable in this change folder enumerates every write to `link_item_*`, `sram_progress_*`, `link_has_crystals`, `link_bottle_info[*]`, heart-piece/heart-container counters, and equivalent state, classified as (grant site / state-shuffle / cosmetic / progress-flag). Grant sites are mapped to ALTTPR location IDs. The deliverable also lists item types needing new receive paths (small key, single rupee, etc.). This audit is the source of truth for what `randomizer-placement` must dispatch and is checked in as `audit.md` in the change folder before any 6.x task begins.

## Impact

- **Code touched**: new `src/rando/` module (generator, logic VM, placement, RNG, share-string, spoiler, save sidecar). Single-line dispatch additions at every grant site listed in the audit deliverable, across `dungeon.c`, `sprite.c`, `sprite_main.c`, `messaging.c`, `misc.c`, `ancilla.c`, `player.c`. New file-select layout work in `select_file.c`. New HUD overlays in `hud.c`. New text-input plumbing in `main.c` (SDL_TEXTINPUT) and the Switch port (libnx swkbd).
- **`features.h`**: adds `kFeatures1_*` bank and a small `kRam_*` block. The free range after the existing `0x648`-block and `0x650`-block allocations is `0x659-0x66f` (23 bytes); `0x670` begins `spotlight_var3` per [variables.h:556](src/variables.h:556). To stay well inside this range and avoid a tight squeeze, **only the master state lives in `g_ram`**; everything else (settings struct, settings_hash full 16 bytes, share string, placement table) lives in heap inside `src/rando/`. Required g_ram cells: `kRam_Features1 = 0x659` (uint32, 4 bytes) + `kRam_RandoSlotActive = 0x65d` (1 byte) + `kRam_RandoStartingInventoryGranted = 0x65e` (1 byte) = 6 bytes total, ending at 0x65f. Final offsets are confirmed during Phase 0 task 0.7 (which scans every macro in `variables.h`/`features.h` to verify no overlap before pinning).
- **Save storage**: new `saves/sram_rando.dat` sidecar with **3 slots** mirroring `sram.dat`'s 3-slot layout (per [messaging.c:103](src/messaging.c:103) `kSrmOffsets[4]` — which is 3 primaries + 1 backup-region base, not 4 slots; the 8 KB SRAM has no room for a 4th slot). Each sidecar slot is **80-byte header + embedded placement table + checked-location bitmap** (authoritative byte-offset layout in `randomizer-save / Sidecar slot contents`). The 80-byte header carries magic, slot_kind, generator_version, 16-byte settings_hash, 32-byte raw share-string binary, last_vanilla_write_version, `sram_slot_checksum_at_last_write`, **`placement_table_size` (uint16 LE)**, flags, plus a 16-byte reserved tail for forward-compat. The bitmap is sized by `(placement_table_size/2 + 7) >> 3` bytes (~27 bytes for Phase A's ~212-location baseline; varies by world-state). `placement_table_size` is **required** for cross-version upgrade safety — a v1.1 binary reading a v1.0 slot reads exactly the older slot's table size; if the registry grew, the new locations are unchecked-default (per `randomizer-save / Checked-location bitmap read invariant`). Atomic-commit semantics are write-temp + fsync + rename (no in-slot commit byte). The spoiler file path is derived at runtime from `[randomizer] spoiler_dir` + share string, not stored in the slot. Existing `sram.dat` is byte-untouched.
- **Assets**: no changes to `zelda3_assets.dat` format. The generator works against item/location IDs already encoded in vanilla game data, plus the YAML-driven logic graph compiled into a new C array.
- **Config**: new `[randomizer]` section in `zelda3.ini` (default settings, spoiler-log output directory, tracker keybindings, race-mode default).
- **Dependencies**: no new runtime libraries. Vendored single-file SHA-256 implementation under `third_party/sha256/` for the settings hash.
- **Build**: new `.c` files added to the existing Makefile glob (`src/rando/*.c`); MSVC project file updated; Switch makefile updated. New codegen rule for `src/rando/logic_data.c` ← `assets/rando/logic.yaml`, wired into Make, MSVC pre-build, and Switch make.
- **Determinism scope**: same `(generator_version, settings, seed_u64)` produces an identical placement table across Linux, macOS, Windows, and Switch builds, validated by a CI corpus diff. We make **no** claim of placement compatibility with alttpr.com; share strings are not cross-compatible in either direction.
